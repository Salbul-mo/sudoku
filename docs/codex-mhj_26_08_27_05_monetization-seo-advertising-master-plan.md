## 0. 최종 결론

현재 프로젝트에서 단기간에 광고 매출을 기대하는 것은 현실적이지 않다. 검색엔진에
등록되지 않았거나 방문·완주 데이터가 없는 상태에서는 광고 승인 가능성, 실제 광고
노출률, `eCPM`, 사용자 이탈을 판단할 수 없기 때문이다.

가장 현실적인 전략은 다음 세 경로를 순서대로 검증하는 것이다.

1. **검색·측정 기반 확보**
   - 최신 버전 배포
   - 독립 도메인과 서비스명 확정
   - Google·Naver·Bing 등록
   - 검색 메타데이터·favicon·공유 이미지·JSON-LD 정비
   - 방문·완주·재시작·재방문 기준선 확보
2. **직접 수익 검증**
   - 접근성 중심 화이트라벨을 기관 20곳에 제안
   - 인쇄용 퍼즐 샘플과 유료 묶음을 최소 비용으로 검증
   - 게임 생성·접근성 구현을 개발 포트폴리오와 컨설팅 리드로 활용
3. **조건부 광고 실험**
   - 일반 AdSense와 H5 Games Ads 승인을 받은 뒤
   - Rush의 완료 후 `다시 하기`에서 전면 광고를 먼저 시험
   - 수익과 재시작·재방문 지표가 모두 통과할 때만 Classic으로 확대

### 핵심 판단

> 게임 UI는 무료·집중형으로 유지하고, 검색 유입은 별도의 기능형 페이지와 외부
> 발견 경로로 확보한다. 첫 직접 수익은 광고보다 화이트라벨·개발 의뢰·인쇄 공급에서
> 검증하고, 광고는 충분한 완주량과 승인이 확인된 뒤 Rush에서만 작게 시작한다.

### 조건을 전혀 완화하지 않을 때의 현실

다음 조건을 모두 유지하면 검색 유입과 수익 발생 가능성은 매우 낮다.

- 게임 화면 변경 없음
- 사용자가 볼 수 있는 별도 기능 페이지 없음
- 외부 기술 글·커뮤니티·디렉터리 홍보 없음
- 직접 영업 없음
- 앱·게임 포털 배포 없음
- 메타데이터만 변경

메타데이터는 색인과 검색 결과 표현을 돕지만 사이트 권위·사용 가치·외부 링크를
대체하지 못한다.

## 1. 프로젝트에서 확정된 제품 원칙

지금까지의 대화와 구현에서 다음 원칙이 확정됐다.

### 1.1 퍼즐 생성

- 사용자가 난이도를 선택해 새 퍼즐을 만드는 구조를 유지한다.
- 난이도마다 지정된 단서 수 구간에서 암호학적 난수를 사용해 목표 단서 수를 정한다.
- 퍼즐 생성에 시드를 사용하지 않는다.
- 단서를 하나씩 제거할 때마다 유일해를 확인한다.
- 반환 직전에도 전체 유일해를 다시 검증한다.
- 광고·검색 기능 때문에 실시간 퍼즐 생성 성능이 느려지면 안 된다.

### 1.2 난이도

- 웹 실시간 생성은 단서 수 구간 기반 난이도를 사용한다.
- 사용자에게는 단서 수 자체보다 난이도 이름을 표시한다.
- 단서 수와 인간 풀이 난이도가 완전히 일치한다고 주장하지 않는다.
- 출판 계약에서 정밀 난이도를 보증해야 할 때만 오프라인 풀이 기법 분석을 추가한다.
- 오프라인 분석은 실시간 생성 API의 응답시간에 영향을 주지 않도록 분리한다.

### 1.3 UI와 설명

- 사용자는 스도쿠 규칙을 이미 안다고 가정한다.
- 게임 화면에 긴 규칙 설명이나 SEO용 본문을 추가하지 않는다.
- 검색 노출을 위한 숨은 설명문, 화면 밖 텍스트, 키워드 반복을 사용하지 않는다.
- 개인정보처리방침·광고 고지처럼 법적·정책상 필요한 링크는 작고 명확한 footer로
  제공할 수 있다.

### 1.4 광고

- 게임판과 조작 버튼 주변에 일반 광고를 배치하지 않는다.
- 자체 모달 안에 일반 AdSense 광고 단위를 삽입하지 않는다.
- 광고가 퍼즐 생성·게임 시작을 영구적으로 막으면 안 된다.
- 광고가 필요하다면 완료 후 다음 게임으로 넘어가는 자연 전환 지점에 제한한다.

## 2. 현재 상태 실사

### 2.1 제품 기능

현재 제품은 다음 페이지를 제공한다.

| 언어 | Classic | Rush |
|---|---|---|
| 한국어 | `/` | `/rush/` |
| 영어 | `/en/` | `/en/rush/` |

Classic은 다음 기능을 제공한다.

- 난이도 선택과 매번 새로 생성되는 퍼즐
- 키보드·터치 입력
- 후보 숫자
- 정답 체크와 충돌 강조
- 진행 상태 저장·복구
- 설정·도움말·공유
- 다크 모드와 접근성 고려

Rush는 다음 기능을 제공한다.

- 제한시간 내 한 칸씩 입력
- 점수·콤보·생명
- 게임 종료 결과 패널
- `다시 하기`
- 다음 퍼즐 사전 요청

### 2.2 생성 엔진과 배포

- 정적 자산: `game/static`
- 동적 API: `/api/new-puzzle/`
- 생성 방식: Cloudflare Pages Function의 DLX 기반 생성·유일해 검증
- 사용자 계정: 없음
- 데이터베이스·KV·R2: 없음
- 결제: 없음
- 광고: 없음
- 분석 비콘: 없음
- 개인정보처리방침·CMP: 없음
- `ads.txt`: 없음
- Content Security Policy: 없음

현재 구조는 운영비가 낮고 개인정보 수집이 적다는 장점이 있다. 광고·계정·글로벌
오늘의 퍼즐을 추가하면 이 단순성이 줄어든다.

### 2.3 검증된 품질

- 생성 퍼즐은 제거 단계와 반환 단계에서 유일해를 확인한다.
- 기존 2,900개 퍼즐 생성 테스트에서 유일해가 확인됐다.
- 이 결과는 테스트 당시의 구현과 입력 범위에 대한 근거이며 미래 코드 변경의 영구
  보증은 아니다.
- 광고나 수익화 변경 후에도 생성·유일해 테스트를 회귀 게이트로 유지해야 한다.

### 2.4 공개 배포 상태

2026-08-27 조사 당시 네 개 공개 페이지와 `robots.txt`, `sitemap.xml`은 HTTP `200`을
반환했다. 다만 공개 Classic 메타데이터 일부는 로컬 최신 난이도 표현보다 오래된
설명을 사용하고 있어 최신 정적 파일 배포가 우선 과제다.

Search Console·Naver Search Advisor·Bing Webmaster Tools 계정 데이터에는 접근하지
못했으므로 실제 색인, 노출, 클릭, 검색어, 평균 위치는 미확인이다.

## 3. 검색 노출 전략

### 3.1 색인과 순위는 별개다

검색 노출 문제는 두 단계로 나눠야 한다.

1. **색인 문제**
   - 검색엔진이 URL을 발견하고 저장했는가
2. **순위 문제**
   - 발견된 URL이 특정 검색어에서 다른 사이트보다 높은가

Search Console 등록과 sitemap 제출은 색인 상태를 확인하고 오류를 찾는 작업이다.
그 자체가 높은 순위를 보장하지 않는다.

### 3.2 UI를 바꾸지 않고 가능한 작업

- 최신 4개 페이지 배포
- URL별 고유 `title`과 `meta description`
- 자기 참조 canonical
- 한국어·영어 `hreflang` 상호 참조
- `x-default`
- 정확한 sitemap
- Google Search Console 소유 확인과 URL 검사
- Naver Search Advisor 소유 확인과 sitemap 제출
- Bing Webmaster Tools 등록 또는 Google 설정 가져오기
- 변경 시 Naver·Bing IndexNow 알림
- 고유 서비스명과 독립 도메인
- `WebSite` JSON-LD
- 실제 기능에 맞는 `SoftwareApplication`·`VideoGame` JSON-LD
- 48px 배수 favicon
- Classic·Rush별 `1200×630` 공유 이미지
- `og:image`, `twitter:image`
- Cloudflare Web Analytics

권장 검색 제목:

| URL | 권장 제목 |
|---|---|
| `/` | `무료 온라인 스도쿠 게임 | 난이도별 새 퍼즐` |
| `/en/` | `Free Online Sudoku Game | New Puzzle by Difficulty` |
| `/rush/` | `스도쿠 러시 | 무료 타임어택 스도쿠 게임` |
| `/en/rush/` | `Sudoku Rush | Free Timed Sudoku Game` |

`meta keywords`는 추가하지 않는다. Google은 이를 검색 순위에 사용하지 않는다.

### 3.3 메타데이터만으로 해결되지 않는 부분

현재 사이트는 네 개의 앱 셸 페이지가 전부다. Google은 JavaScript를 렌더링할 수
있지만 검색 관련성과 신뢰를 메타데이터만으로 충분히 만들 수는 없다. 일반적인
`스도쿠` 한 단어는 대형 앱·게임·미디어와 경쟁하므로 단기 목표로 부적절하다.

현실적인 목표 검색어:

- `무료 온라인 스도쿠 게임`
- `설치 없는 스도쿠`
- `스도쿠 러시`
- `타임어택 스도쿠`
- `유일해 스도쿠`
- `접근성 스도쿠`
- `키보드 스도쿠`

### 3.4 별도 기능형 페이지

게임 화면을 건드리지 않고 검색 대상과 수익 검증을 늘리려면 설명용 글이 아니라 실제
기능을 제공하는 별도 URL을 만든다.

#### `/daily-sudoku/`

- 매일 하나의 공통 퍼즐
- 기존 랜덤 생성기로 한 번 생성한 뒤 저장
- 시드 사용 없음
- 퍼즐 ID로 조회
- 날짜·난이도·기록·공유

전 세계 공통 퍼즐을 제공하려면 서버 측 영속 저장소가 필요하다. 로컬 전용
`오늘의 1판`은 `localStorage`만으로 가능하지만 사용자끼리 같은 퍼즐을 공유하지는
못한다.

#### `/printable-sudoku/`

- 실제 무료 샘플 PDF
- 난이도별 퍼즐과 정답
- 인쇄 여백과 페이지 구성
- 유료 묶음 또는 기관 문의 연결

#### `/business/`

- 기관 임베드·화이트라벨 범위
- 한국어·영어, Classic·Rush 선택
- 접근성 테스트 범위
- 문의 방법

게임 사용자는 이 페이지를 읽을 필요가 없다. 작은 footer 또는 sitemap을 통해 실제
탐색 경로만 제공한다.

### 3.5 외부 발견 경로

자체 게임 화면에 설명을 넣지 않으려면 설명과 신뢰를 외부에 만든다.

- 공개 저장소 README의 라이브 데모
- DLX Worker 이식 과정 기술 글
- 유일해 검증과 테스트 방법 글
- 키보드·스크린리더 접근성 구현 사례
- 웹 게임·오픈소스·접근성 디렉터리
- 관련 커뮤니티의 실제 소개·사용 후기
- 완주 결과 공유 카드와 동일 퍼즐 도전 링크

링크 구매, 자동 디렉터리 대량 등록, 키워드 앵커 반복, 트래픽 교환은 사용하지 않는다.

### 3.6 금지할 SEO 방식

- 화면 밖에 설명문 배치
- 투명 글자 또는 배경색과 같은 글자
- 사용자와 검색봇에게 다른 콘텐츠 제공
- 난이도만 바꾼 중복 페이지 대량 생성
- 실제 제공하지 않는 가격·평점·리뷰 구조화 데이터
- sitemap의 `lastmod`를 빌드할 때마다 현재 날짜로 조작
- 키워드 반복과 자동 생성된 저가치 본문

## 4. 재미와 재방문 강화

검색 유입이 생겨도 한 번 플레이하고 떠나면 광고·직접 판매 모두 성장하기 어렵다.
게임의 규칙 설명을 늘리지 않고 재미를 높일 수 있는 후보는 다음과 같다.

### 4.1 우선순위가 높은 후보

1. 완주 결과 카드
   - 난이도
   - 시간
   - 실수 수
   - 힌트 사용 여부
   - 개인 최고 기록
2. 로컬 개인 기록
   - 난이도별 최고 시간
   - 총 완주 수
   - 연속 완주
3. 로컬 오늘의 1판
   - 해당 날짜 첫 랜덤 생성 결과를 `localStorage`에 보존
   - 시드 불필요
4. Rush 기록 강화
   - 최고 점수
   - 최고 콤보
   - 최근 기록 비교
5. 공유 링크
   - 동일 퍼즐 도전이 필요하면 퍼즐 자체 또는 서버 저장 퍼즐 ID 사용
   - 시드 기반 재생성은 사용하지 않음

### 4.2 실험 원칙

- 한 번에 기능 하나만 추가
- 완주·재시작·재방문 변화를 비교
- 퍼즐 생성 성능과 Core Web Vitals 유지
- 접근성 회귀 없음
- 효과가 없으면 추가 확장 중단

| 접근성 화이트라벨 | 중간 | 중간 | 핵심 게임 낮음 | 낮음 | 1 |
| 포트폴리오·개발 의뢰 | 낮음 | 중간 | 없음 | 낮음 | 2 |
| 인쇄·출판 공급 | 중간 | 낮음~중간 | 없음 | 중간 | 3 |
| H5 게임 광고 | 중간 | 승인·트래픽 이후 | 전면 광고 | 매우 높음 | 4 |
| 퍼즐 생성 API | 높음 | 사전 문의 없으면 낮음 | 없음 | 고객 영업 | 5 |
| 소비자 구독 | 매우 높음 | 낮음 | 계정·결제 필요 | 높음 | 6 |
| 후원·기부 | 낮음 | 낮음 | 작은 링크 | 높음 | 보조 |

### 5.1 접근성 화이트라벨

잠재 고객:

- 노인복지관·시니어 프로그램
- 도서관·문화센터
- 교육기관
- 접근성 요구가 있는 포털·미디어
- 자체 게임 개발 인력이 없는 콘텐츠 사업자

제공 범위:

- 브랜드·색상 교체 가능한 임베드
- 자체 도메인 설치형
- Classic 또는 Rush
- 한국어·영어
- 키보드·스크린리더 지원
- 테스트 결과와 유지보수 범위

자동 테스트 통과를 공식 인증으로 판매하면 안 된다. 납품 전 수동 스크린리더,
모바일, 브라우저 검수와 계약 범위 정의가 필요하다.

수요 검증:

- 적격 대상 20곳에 제품 사양과 데모 제안
- 문제 인터뷰 2건 이상 또는 유상 견적 요청 1건을 통과 기준으로 사용
- 20곳 모두 무응답이면 대규모 제품화 중단

### 5.2 포트폴리오·개발 의뢰

현재 바로 사용할 수 있는 근거:

- DLX 기반 생성기
- 유일해 불변식
- 단서 구간 생성 검증
- Cloudflare Worker 성능
- 키보드·터치·스크린리더
- 명암비·회귀 테스트
- 무상태 배포

게임 자체 매출이 작더라도 기술·접근성·성능 컨설팅의 신뢰 자료가 된다. 검색용 외부
기술 글과 B2B 영업 자료를 동시에 해결할 수 있다.

### 5.3 인쇄·출판

필요한 제품화:

- 대량 배치 생성
- 중복 퍼즐 검출
- 정답지 자동 편집
- PDF/SVG 출력
- 페이지 여백·퍼즐 수 템플릿
- 출판용 오프라인 난이도 분석

초기에는 무료 샘플과 한 개의 유료 묶음을 수작업으로 제공한다. 실제 구매 10건 같은
검증 기준을 넘은 뒤 자동화를 개발한다. 가격과 지불 의사는 아직 검증되지 않았다.

### 5.4 퍼즐 생성 API

추가로 필요한 요소:

- API key
- rate limit
- 사용량 계측
- 청구·환불
- 버전 정책
- SLA와 고객지원
- 남용·비용 통제

실제 문의나 파일럿 없이 이를 먼저 만들면 운영 시스템만 늘어난다. 적격 문의가 여러
건 발생한 뒤 제품화한다.

### 5.5 광고

광고는 대규모 사용량에서 자동으로 수익이 발생한다는 장점이 있지만, 승인·정책·동의·
사용자 이탈 비용이 있다. 현재 단일 페이지 구조에서는 새 퍼즐 10회가 페이지뷰 10회가
아니므로 일반 페이지 RPM만으로 게임 활동을 수익화하기 어렵다.

## 6. 광고 상품 연구 결과

| 광고 방식 | 적합도 | 판단 |
|---|---:|---|
| AdSense H5 `Interstitial` | 높음 | 완료 후 다음 게임에 가장 적합 |
| AdSense H5 `Rewarded` | 중간 | 실제 보상 수요가 생긴 뒤 |
| 직접 스폰서 결과 카드 | 중간 | B2B 관계가 있을 때 낮은 트래픽에서도 가능 |
| CrazyGames SDK | 중간 | Rush 외부 유통 실험 |
| Poki SDK | 낮음~중간 | 큐레이션·웹 독점 계약 검토 필요 |
| Auto Ads Vignette | 낮음 | 단일 페이지 게임과 트리거가 맞지 않음 |
| 일반 디스플레이 | 낮음 | 게임과 150px 거리·UI 공간 필요 |
| Anchor·Side rail | 낮음 | 모바일 조작성과 집중도 저하 |

### 6.1 AdSense H5 Games Ads

- 일반 AdSense 사이트 승인이 선행돼야 한다.
- H5 Games Ads는 별도 신청형이며 승인이 보장되지 않는다.
- `Interstitial`과 `Rewarded`를 제공한다.
- `adBreak()`는 광고 표시 명령이 아니라 광고 기회를 선언한다.
- 실제 광고는 재고·동의·빈도·사용자 상호작용에 따라 나오지 않을 수 있다.
- `adBreakDone`은 광고 유무와 관계없이 게임 흐름을 재개하는 기준점이다.
- `data-adbreak-test="on"`으로 실제 광고 요청 없이 통합을 시험할 수 있다.
- `data-ad-frequency-hint`는 최소 평균 간격 힌트이며 서버 설정이 덮어쓸 수 있다.

### 6.2 Auto Ads Vignette

Vignette는 기본적으로 사이트 내부 페이지 이동 사이에서 나타난다. Classic은 API로
퍼즐만 교체하므로 기본 Vignette와 `새 게임`이 연결되지 않는다. 탭 복귀·비활성 후
상호작용 같은 추가 트리거를 허용하면 퍼즐 도중 예기치 않은 광고가 나타날 수 있다.

게임 페이지에서는 제외하고, 향후 인쇄·콘텐츠 페이지 간 이동에서만 검토한다.

### 6.3 일반 디스플레이

Google은 게임과 일반 AdSense 단위를 최소 150px 떨어뜨릴 것을 강하게 권고한다.
현재 UI에서 이를 지키려면 보드 아래 또는 측면에 광고 공간을 추가해야 하므로 UI
비변경 목표와 맞지 않는다.

### 6.4 직접 스폰서

직접 계약 광고는 H5 승인을 필요로 하지 않는다.

- 결과 화면 아래 `광고` 또는 `후원` 명시
- 이미지·한 문장·외부 링크
- 자동 재생 없음
- 게임 진행과 분리
- 노출·클릭을 수집하면 처리방침 공개

트래픽이 적어도 관련 기관 한 곳과 고정 계약을 체결할 수 있다는 장점이 있지만 직접
영업이 필요하다.

### 6.5 게임 포털

#### CrazyGames

- Basic Launch: 7~21일
- 최소 7일과 500 plays 이후 성과 평가 가능
- Basic Launch 수익화 없음
- Full Launch에서 SDK 광고와 수익 배분 활성화
- 평균 플레이·D1 유지율·플레이 전환율이 핵심
- 외부 광고 SDK 사용 불가

Rush는 Classic보다 짧은 반복 루프와 점수 구조가 있어 포털 적합도가 높다.

#### Poki

- 게임 선별과 최종 심사
- 웹 독점 계약 선호
- 기본 5년은 공식 설명의 참고 조건이며 실제 계약이 우선
- Poki 유입 사용자의 수익은 공식 설명상 50:50
- 직접 검색·북마크·자체 커뮤니티 유입은 개발자 100%
- 비독점은 일회성 라이선스가 될 수 있음

자체 웹사이트와 여러 포털을 유지하려면 독점 범위를 계약서에서 검토해야 한다.

## 7. 모달·전면 광고 설계

### 7.1 핵심 원칙

기존 `DialogHost` 안에 광고를 넣지 않는다. 기존 게임 모달을 완전히 닫은 뒤 Google
H5 API가 전체 화면 광고를 관리하게 한다.

이유:

- 기존 `DialogHost`는 중첩 모달을 허용하지 않음
- 배경 `inert`와 광고 iframe 포커스 충돌 가능
- 난이도·닫기 버튼과 광고의 우발 클릭 위험
- 광고 UI·닫기 제어를 임의로 감싸는 정책 위험
- 키보드·스크린리더 포커스 복원 복잡성

### 7.2 Classic 흐름

```text
퍼즐 완주
  -> 완료 상태 표시
  -> 사용자가 새 게임 선택
  -> 난이도 모달
  -> 난이도 선택
  -> 모달 닫힘
  -> 광고 적격성 확인
       -> 부적격/광고 없음/오류 -> 새 퍼즐
       -> 적격 -> H5 Interstitial -> 새 퍼즐
```

조건:

- 완료된 퍼즐 뒤에만 광고 기회
- 미완성 게임 포기에는 광고 없음
- 첫 게임에는 광고 없음
- 완료 2회마다 기회 1회
- 마지막 광고 후 최소 10분

### 7.3 Rush 흐름

```text
게임 종료
  -> 점수·콤보 결과 표시
  -> 사용자가 다시 하기 선택
  -> 광고 적격성 확인
       -> 부적격/광고 없음/오류 -> game.start()
       -> 적격 -> H5 Interstitial -> game.start()
```

조건:

- 종료 3회마다 기회 1회
- 마지막 광고 후 최소 10분
- 결과를 표시하기 전에 광고하지 않음
- 사용자 `다시 하기` 의사가 있어야 함

Rush가 첫 광고 실험 대상이다. 게임 종료와 재시작 경계가 명확하고 다음 퍼즐을 이미
미리 요청하기 때문이다.

### 7.4 생성 속도 유지

Classic에서는 난이도 선택 후 퍼즐 요청과 광고 기회를 병렬로 실행한다.

```text
난이도 선택
 ├─ /api/new-puzzle/ 요청·유일해 응답 검증
 └─ H5 광고 기회
          ↓
광고 흐름과 퍼즐 응답이 모두 끝나면 보드 교체
```

광고가 나오지 않으면 퍼즐 응답 즉시 시작한다. 광고가 표시되면 퍼즐 생성은 그
시간에 백그라운드에서 완료될 수 있다. 생성 알고리즘·시드 금지·유일해 검증은
변경하지 않는다.

현재 `restart()`는 요청과 보드 반영이 한 흐름이므로 실제 구현에서는 내부만
“요청·검증”과 “세션 반영”으로 분리한다. 공개 API와 설정 키는 유지한다.

### 7.5 실패 허용 구조

광고는 항상 `fail-open`이어야 한다.

- 광고 API 준비 안 됨 → 게임 계속
- 광고 재고 없음 → 게임 계속
- frequency cap → 게임 계속
- 동의하지 않음 → 게임 계속
- 광고 차단 → 게임 계속
- 네트워크 오류 → 게임 계속
- 초기화 timeout → 게임 계속

광고 초기화 제한시간은 2초를 초기값으로 검토한다. 광고 오류와 퍼즐 API 오류는 서로
다른 메시지와 계측 경로를 가져야 한다.

### 7.6 보상형 광고

가능한 후보:

- Classic 힌트 1회
- Rush 생명 1개
- Rush 제한시간 추가

사용자가 광고와 보상을 명확히 알고 동의해야 하며, 거절해도 정상 게임 이용이
가능해야 한다. 현재는 광고를 위해 보상 기능부터 만들지 않는다.

## 8. 광고 승인·개인정보·정책

### 8.1 승인 순서

1. 독립 도메인 또는 승인 가능한 사이트 주소 준비
2. 실제 운영자·문의 정보
3. 개인정보처리방침
4. AdSense 소유 확인
5. 사이트 전체 심사와 `Ready`
6. `ads.txt`
7. H5 Games Ads 별도 신청
8. 승인 후 테스트 모드 구현

Google은 일반 AdSense와 H5 Games Ads의 공개 최소 트래픽을 제시하지 않는다. 현재
네 개 앱 셸만으로는 “충분한 고유 콘텐츠” 심사 위험이 있으므로 실제 기능형 페이지와
탐색 구조를 먼저 준비한다.

### 8.2 도메인

`pages.dev`는 Public Suffix List에 포함돼 있어 하위 사이트 등록 가능성을 배제할 수
없다. 그러나 다음 이유로 독립 도메인이 더 적절하다.

- 광고 계정 소유권
- 루트 `ads.txt`
- 검색 canonical 통합
- 브랜드와 직접 광고 신뢰
- 플랫폼 이전 가능성

독립 도메인 연결 후 `pages.dev`를 301 리다이렉트하고 AdSense·canonical·sitemap을
최종 도메인으로 통일한다.

### 8.3 개인정보처리방침

광고 도입 전 실제 처리 내용에 맞춰 다음을 공개한다.

- Google과 제3자 광고 사업자
- 쿠키·행태정보 수집 목적
- 맞춤 광고 여부
- 광고 거부 방법
- 제3자 사업자와 링크
- 자체 이벤트 수집 항목·보존기간
- 문의·권리 행사 방법

EEA·영국·스위스의 맞춤 광고에는 Google 인증 CMP와 IAB TCF 연동이 요구된다.
미국 적용 주의 거부 메시지도 검토해야 한다. 한국 개인정보보호위원회의 2026 처리방침
지침에 따라 행태정보 수집·이용·제공과 거부 방법을 투명하게 작성한다.

광고를 도입하면 개인정보 링크와 필요한 동의 UI가 생기므로 “화면 완전 무변경”은
불가능하다. 게임판을 건드리지 않는 footer와 지역별 동의 메시지로 영향 범위를 줄인다.

### 8.4 정책상 피해야 할 배치

- 첫 랜딩 전체 화면 광고
- 첫 게임 전 강제 광고
- 마지막 숫자 입력 즉시 예고 없는 광고
- 플레이 중 탭 복귀 광고
- 난이도 버튼과 광고의 한 모달 배치
- 매 입력·매 셀·매 힌트 광고
- 광고를 닫지 않으면 게임 불가
- 일반 광고 단위 자동 새로고침
- 자체 광고 클릭·지인 클릭 요청
- “사이트 지원”을 이유로 광고 클릭 유도

### 8.5 검색과 성능

방문 직후 본문을 가리는 침입형 interstitial은 검색 성과와 사용자 신뢰를 해칠 수
있다. 완료 후 사용자가 다음 게임을 요청할 때 표시하는 광고는 상대적으로 위험이
낮지만 검색 영향이 없다고 보장할 수는 없다.

광고 태그는 외부 JavaScript·iframe을 추가해 LCP·INP·CLS에 영향을 줄 수 있다.
광고 전후 Core Web Vitals를 비교하고, 일반 광고 슬롯을 사용할 경우 크기를 미리
예약한다.

## 9. 광고 수익 민감도

Google은 이 사이트의 H5 광고 `eCPM`, fill rate, 노출률을 보장하지 않는다. 아래는
예측이 아니라 산술 시나리오다.

가정:

- 완료 2회당 광고 기회 1회: `50%`
- 광고 기회 중 실제 노출: `60%`
- 완료 1회당 실제 광고 노출: `0.3회`

계산식:

```text
광고 기회 = 완료 × 0.5
실제 노출 = 광고 기회 × 0.6
매출 = 실제 노출 ÷ 1,000 × eCPM
```

| 월 완주 | 광고 노출 | eCPM $0.5 | eCPM $2 | eCPM $5 | eCPM $10 |
|---:|---:|---:|---:|---:|---:|
| 10,000 | 3,000 | $1.50 | $6 | $15 | $30 |
| 50,000 | 15,000 | $7.50 | $30 | $75 | $150 |
| 100,000 | 30,000 | $15 | $60 | $150 | $300 |
| 500,000 | 150,000 | $75 | $300 | $750 | $1,500 |

계정 통화가 USD이고 지급 기준이 $100인 경우 같은 가정에서 필요한 누적 완주량:

| eCPM 가정 | 필요한 광고 노출 | 필요한 완주 |
|---:|---:|---:|
| $0.5 | 200,000 | 약 666,667 |
| $2 | 50,000 | 약 166,667 |
| $5 | 20,000 | 약 66,667 |
| $10 | 10,000 | 약 33,334 |

실제 지급 통화, 광고 보고서, 노출률이 나오면 이 시나리오를 관측값으로 교체한다.

### 현실적인 해석

- 월 완주가 수천 회라면 광고 수익은 운영 복잡도보다 작을 가능성이 높다.
- 월 완주 100,000회도 `eCPM $2` 가정에서는 월 $60이다.
- 광고는 트래픽을 만드는 수단이 아니라 이미 존재하는 트래픽을 수익화하는 수단이다.
- 첫 수익만 목표라면 한 건의 화이트라벨·개발 의뢰가 장기간 광고보다 클 수 있다.

## 12. 광고 실험 계획

### 12.1 선행 게이트

- [ ] 독립 도메인 또는 AdSense 승인 주소
- [ ] AdSense `Ready`
- [ ] H5 Games Ads 승인

- [ ] CMP·거부 경로
- [ ] `ads.txt` Authorized
- [ ] 무광고 28일 기준선
- [ ] 테스트 광고 전체 경로 통과
- [ ] 광고 차단 상태 게임 정상
- [ ] 모바일·키보드·스크린리더 검증

### 12.2 Rush 우선 롤아웃

1. 테스트 모드 100%
2. 실제 사용자 10%
3. 충분한 표본까지 관찰
4. 25%
5. 광고·무광고 50% 비교
6. 수익과 유지율을 모두 통과하면 확대

한 번에 빈도·배치·형식 중 하나만 변경한다.

### 12.3 중단 기준

아래 값은 광고 플랫폼 규칙이 아니라 프로젝트 내부 안전 기준이다.

- 광고·CMP 때문에 새 게임이 막히는 오류가 재현되면 즉시 중지
- 광고 경로 기술 오류율 `0.5%` 초과 시 확대 중지
- 다음 게임 시작률이 대조군보다 `5%p` 이상 반복 하락하면 중지
- D1·D7 재방문이 악화되면 빈도 축소 또는 중지
- Core Web Vitals가 `good` 범위를 벗어나면 확대 중지
- 정책·무효 트래픽 경고 시 해당 배치 즉시 중지
- 완료 1,000회당 수익이 운영 최소값보다 낮으면 중지

광고 매출이 증가해도 완주와 재방문 감소가 더 크면 실패다.

## 13. 개발 구현 단계

실제 기능 개발은 저장소의 `$staged-development` 절차에 따라 단계별 승인을 받아야
한다.

### 1. System Design

- 최종 도메인과 canonical 구조
- 분석 이벤트와 개인정보 범위
- 기능형 검색 페이지 선택
- 광고 어댑터·CMP·fail-open 구조
- Classic 퍼즐 요청 병렬화 경계

### 2. Macro Blocking

- SEO 정적 자산
- 검색엔진 등록 작업
- 측정 기반
- 개인정보·CMP
- AdSense·H5 승인
- Rush 광고 실험
- Classic 조건부 확대

### 3. Micro Blocking

- 파일별 수정 계획
- 이벤트 상태 전이
- 광고 빈도 저장 구조
- `adBreakDone` 단일 완료 보장
- timeout·차단·무재고 처리
- 테스트 케이스와 롤백 조건

### 4. Code Implementation

- 승인된 최소 범위만 수정
- 신규 파일은 `codex-mhj_YY_MM_DD_<sequence>_` 접두어
- 공개 인터페이스·설정 키 유지
- 퍼즐 생성·유일해 검증 회귀 테스트
- UI·접근성·성능 검증
- 실제 광고 대신 테스트 모드 검증

여러 수익모델과 광고 SDK를 동시에 구현하지 않는다.

## 16. 최종 의사결정 기준

### 검색

- 색인되지 않았다면 기술 등록 문제를 먼저 해결한다.
- 색인됐지만 노출이 없다면 목표 검색어와 외부 발견 경로를 검토한다.
- 세 개의 연속 28일 구간에서도 노출이 거의 없으면 메타데이터 미세 조정을 중단한다.

### 직접 수익

- 20개 적격 기관에서 인터뷰 2건 또는 유상 견적 1건이 나오면 제품화한다.
- 반응이 없으면 인증·계정·청구를 만들지 않는다.
- 인쇄 상품은 실제 구매가 발생한 뒤 자동화한다.

### 광고

- 일반 AdSense와 H5 승인이 모두 필요하다.
- Rush에서 먼저 시험한다.
- 충분한 완주량 없이 수익성을 가정하지 않는다.
- 광고 후 다음 게임·재방문 감소가 수익보다 크면 제거한다.

### 전체 사업

> 수익이 전혀 없더라도 검색·접근성·생성 엔진을 포트폴리오 자산으로 남길 수 있다.
> 반대로 수요가 검증되지 않은 광고·계정·결제 시스템은 유지비만 남긴다. 모든 확장은
> 관측 데이터 또는 실제 고객 요청을 통과 조건으로 삼는다.

## 19. 운영 기준선과 측정 상태

### 19.1 현재 확인 상태

저장소 실사만으로는 실제 운영 트래픽, 검색 노출, 광고 승인 여부와 사용자 행동을
확인할 수 없다. 따라서 아래 운영 수치는 모두 **현재 미측정**으로 분류한다. 숫자를
추정해 기준선처럼 사용하지 않는다.

| 지표 | 정확한 정의 | 권장 출처 | 현재 상태 | 최소 관찰 기간 |
|---|---|---|---|---:|
| 검색 노출 | 검색 결과에 URL이 표시된 횟수 | Search Console·Search Advisor | 현재 미측정 | 28일 |
| 검색 클릭 | 검색 결과에서 실제 방문한 횟수 | Search Console·Search Advisor | 현재 미측정 | 28일 |
| 자연검색 방문 | 광고·직접 방문을 제외한 검색 유입 세션 | Web Analytics | 현재 미측정 | 28일 |
| 게임 시작 | 플레이 가능한 퍼즐이 표시되고 입력을 받을 수 있게 된 횟수 | 자체 이벤트 | 현재 미측정 | 28일 |
| 퍼즐 완주 | 유일해 정답과 일치해 완료 상태가 확정된 횟수 | 자체 이벤트 | 현재 미측정 | 28일 |
| 완주율 | 퍼즐 완주 수 ÷ 게임 시작 수 | 자체 집계 | 현재 미측정 | 28일 |

| D7 재방문 | 첫 방문 7일 후 다시 게임을 시작한 익명 사용자 비율 | 개인정보 최소 분석 | 현재 미측정 | 42일 |

| `LCP`·`INP`·`CLS` | 실제 사용자 기준 Core Web Vitals | Search Console·RUM | 현재 미측정 | 28일 |

### 19.2 기준선 고정 규칙

1. 광고 SDK와 CMP를 넣기 전에 연속 28일을 무광고 기준선으로 기록한다.
2. 배포일, 장애일, 봇 트래픽 급증일은 별도로 표시하되 원본 데이터에서 임의 삭제하지
   않는다.
3. 광고 실험군과 대조군은 같은 기간, 같은 모드, 같은 기기 범주에서 비교한다.
4. 검색 지표는 주말·공휴일 영향을 줄이기 위해 같은 길이의 기간과 비교한다.
5. 생성 속도는 클라이언트 체감시간과 Worker 처리시간을 분리한다.
6. 난이도별 `clue_count` 분포도 함께 기록해 특정 구간 편중을 확인한다.
7. 실제 측정값이 생기면 이 문서의 가정값을 덮어쓰지 않고 관측값 표를 새 날짜로
   추가한다.

### 19.3 핵심 계산식

```text
Completion Rate = puzzle_complete / game_start
Next Game Rate = next_game_start_after_complete / puzzle_complete
Generation Error Rate = failed_generation_request / generation_request
Ad Show Rate = ad_impression / ad_opportunity
Revenue per 1,000 Completions = ad_revenue / puzzle_complete * 1,000
```

`generation_request`에는 네트워크 재시도가 포함될 수 있으므로 사용자 수나 완주 수로
해석하지 않는다.

## 20. 분석 이벤트 명세

### 20.1 공통 원칙

- 이벤트 이름과 필드는 배포 후 의미를 바꾸지 않는다. 의미가 달라지면 새 버전을 쓴다.
- 퍼즐 원문, 정답 전체, 입력한 숫자의 시간순 기록은 분석 시스템으로 보내지 않는다.
- 이름, 이메일, IP 기반 자체 사용자 식별자를 만들지 않는다.
- 퍼즐 생성용 시드를 생성하거나 저장하지 않는다.
- `event_id`는 중복 전송 제거용 무작위 식별자이며 퍼즐 생성과 무관하다.
- `session_puzzle_sequence`는 브라우저 세션 내 증가하는 정수이며 다른 사용자의 퍼즐을
  재현하는 값이 아니다.
- 광고 동의를 거부한 사용자에게 적용되는 분석 범위는 CMP와 처리방침에 맞춰 별도로
  검증한다.

공통 필드는 다음으로 제한한다.

| 필드 | 형식 | 목적 |
|---|---|---|
| `event_name` | string | 이벤트 종류 |
| `event_version` | integer | 스키마 버전 |
| `event_id` | random UUID | 중복 전송 제거 |
| `occurred_at` | UTC timestamp | 발생 시점 |
| `locale` | `ko` 또는 `en` | 언어별 분석 |
| `mode` | `classic` 또는 `rush` | 게임 모드 구분 |
| `difficulty` | 기존 난이도 key | 난이도 구분 |
| `session_puzzle_sequence` | positive integer | 세션 내 판 순서 |

### 20.2 게임 이벤트

| Event | 정확한 발생 조건 | 추가 필드 | 중복 방지 기준 |
|---|---|---|---|
| `game_start` | 퍼즐이 화면에 표시되고 입력 가능 상태가 된 직후 | `clue_count`, `generation_ms` | 판당 1회 |
| `number_input` | 사용자가 빈 칸에 숫자를 확정 입력 | 집계용 `input_method`만 허용 | 원시 이벤트 전송 대신 로컬 집계 권장 |
| `puzzle_complete` | 정답 검증이 성공하고 완료 UI 전환이 확정된 직후 | `elapsed_ms`, `mistake_count`, `hint_use_count` | 판당 1회 |
| `next_puzzle_request` | 사용자가 새 퍼즐 동작을 확정 | `source` | 사용자 동작당 1회 |
| `next_game_start_after_complete` | 완주 후 같은 세션에서 다음 퍼즐이 입력 가능 상태가 됨 | `elapsed_from_complete_ms` | 다음 판당 1회 |
| `rush_end` | 제한시간·종료 조건으로 Rush 결과가 확정 | `completed_count`, `elapsed_ms` | Rush 실행당 1회 |
| `share_result` | 운영체제 공유 또는 복사가 성공 | `share_method` | 성공 동작당 1회 |

`hint_use_count`는 현재 게임에 실제 힌트 기능이 있을 때만 전송한다. 난이도를 결정하는
단서 수인 `clue_count`와 사용자 보조 기능인 힌트 사용 횟수를 혼동하지 않는다.

### 20.3 생성 API 이벤트

| Event | 정확한 발생 조건 | 필드 |
|---|---|---|
| `generation_request` | 클라이언트가 새 퍼즐 API 호출을 시작 | `request_reason`, `difficulty` |
| `generation_success` | 유효한 퍼즐 응답을 받고 클라이언트 검증을 통과 | `status_code`, `generation_ms`, `clue_count` |
| `generation_error` | timeout, 네트워크 오류, 서버 오류 또는 응답 검증 실패 | `error_category`, `status_code`, `elapsed_ms` |

생성 성능 회귀 판단은 난이도별 `p50`, `p95`, 오류율을 함께 사용한다. 광고 도입 전후
퍼즐 생성 알고리즘과 유일해 검증을 변경하지 않는다.

### 20.4 광고 이벤트

| Event | 정확한 발생 조건 | 필드 |
|---|---|---|
| `ad_opportunity` | 내부 빈도·모드·동의 조건을 통과해 광고를 요청할 수 있음 | `placement`, `format` |
| `ad_request` | 승인된 광고 API를 실제 호출 | `provider`, `placement`, `format` |
| `ad_impression` | 사업자 callback 또는 보고서로 실제 노출이 확인됨 | `provider`, `placement`, `format` |
| `ad_closed` | 광고가 닫히고 게임 제어권이 돌아옴 | `provider`, `duration_ms`, `break_status` |
| `ad_error` | 초기화·요청·표시 중 오류 또는 timeout | `provider`, `stage`, `error_category` |
| `reward_granted` | 보상형 광고 완료 조건을 사업자 callback으로 확인하고 보상을 1회 지급 | `provider`, `reward_type` |

`ad_request`를 `ad_impression`으로 간주하지 않는다. 수익 분석은 광고 사업자 보고서와
대조해 실제 노출·수익을 확정한다.

### 20.5 데이터 품질 규칙

- `puzzle_complete` 수가 `game_start`보다 많아지면 중복 또는 세션 경계 오류로 본다.
- `ad_impression`이 `ad_request`보다 많으면 callback 중복 처리부터 점검한다.
- `reward_granted`는 한 광고 기회에 최대 한 번만 허용한다.
- 클라이언트가 offline이면 저장 가능한 최소 이벤트만 재전송하고 `event_id`로 중복을
  제거한다.
- 이벤트 스키마 변경은 처리방침과 대시보드 계산식에 미치는 영향을 함께 검토한다.

## 21. 광고 출시·중지·롤백 Runbook

### 21.1 출시 전 필수 조건

다음 조건이 하나라도 충족되지 않으면 실제 광고를 켜지 않는다.

1. 광고 사업자와 해당 광고 형식의 승인이 확인됐다.
2. 테스트 광고로 Classic·Rush 정상 경로를 통과했다.
3. 동의, 거부, 철회, 광고 차단 상태에서 게임이 모두 정상 동작한다.
4. 광고 기능을 배포 없이 끌 수 있는 kill switch가 검증됐다.
5. 광고 초기화와 표시 timeout이 정의됐다.
6. 광고가 실패해도 다음 퍼즐로 진행하는 `fail-open` 경로가 검증됐다.
7. 개인정보처리방침, CMP, `ads.txt`와 실제 SDK 설정이 일치한다.
8. 무광고 28일 기준선이 저장됐다.
9. 모바일, 키보드, 스크린리더로 광고 전후 포커스 이동을 검증했다.
10. 퍼즐 생성 속도와 유일해 검증 회귀 테스트가 통과했다.

### 21.2 정상 실행 순서

```text
Puzzle Completed
    ├─ Start Next Puzzle Generation
    └─ Evaluate Ad Opportunity
            ├─ Not Eligible → Wait for Puzzle → Show Next Puzzle
            └─ Eligible → Request Approved Interstitial
                    ├─ Shown and Closed → Show Prepared Puzzle
                    ├─ No Fill → Show Prepared Puzzle
                    ├─ Timeout → Show Prepared Puzzle
                    └─ Error → Show Prepared Puzzle
```

광고 준비가 퍼즐 생성을 시작시키거나 지연시키지 않는다. 두 작업을 병렬로 시작하되,
다음 퍼즐이 먼저 준비됐는데 광고가 응답하지 않으면 내부 timeout 후 퍼즐을 우선한다.

### 21.3 권장 내부 안전 기준

아래 값은 광고 사업자의 규칙이 아니라 초기 운영을 위한 프로젝트 기준이다.

| 항목 | 초기 기준 | 조치 |
|---|---:|---|
| 광고 초기화 timeout | 2,000ms | timeout 후 광고 없이 진행 |
| 광고 callback 최종 대기 | 5,000ms | 제어권 복구 후 오류 기록 |
| 광고 경로 기술 오류율 | 0.5% 초과 | 확대 중지 |
| 다음 게임 시작률 변화 | 대조군 대비 `-5%p` 이하 | 해당 배치 중지 |
| 생성 시간 `p95` 변화 | 기준선 대비 10% 초과 악화 | 광고 병렬 처리와 리소스 경합 점검 |
| 게임 진행 차단 오류 | 1회라도 재현 | kill switch 즉시 사용 |
| 정책·무효 트래픽 경고 | 경고 수신 | 해당 광고 배치 즉시 중지 |

timeout은 실제 네트워크 관측값으로 조정하되 게임 진행을 광고 응답에 무기한 묶지
않는다.

### 21.4 점진 배포

1. 테스트 광고와 개발자 트래픽만 허용한다.
2. Rush 실제 트래픽 10%에 적용한다.
3. 최소 7일과 충분한 완주 표본을 모두 만족할 때까지 유지한다.
4. 오류·성능·다음 게임 시작률을 통과하면 25%로 확대한다.
5. 50% 실험군과 50% 대조군을 같은 기간에 비교한다.
6. 수익과 유지율을 함께 통과한 배치만 확대한다.
7. Classic은 Rush 결과를 통과한 뒤 별도 실험으로 취급한다.

### 21.5 장애 대응과 롤백

| 상황 | 즉시 조치 | 후속 확인 |
|---|---|---|
| 게임 진행 차단 | kill switch로 광고 전체 중지 | callback 단일 완료와 timeout 검사 |
| 광고 SDK 로딩 장애 | SDK 요청 중지, 게임만 제공 | 사업자 상태·CSP·네트워크 오류 확인 |
| CMP 장애 | 개인화·광고 요청 중지 | 동의 신호와 처리방침 일치 확인 |
| 정책 경고 | 해당 placement 중지 | 스크린샷·이벤트 로그·정책 근거 보존 |
| 생성 성능 악화 | 광고 코드 비활성화 | main thread·네트워크·Worker 영향 분리 |
| 포커스 손실 | 영향 placement 중지 | 닫기 후 원래 게임 요소로 포커스 복구 |
| 수익 대비 유지율 하락 | 빈도 축소 또는 제거 | 동일 기간 대조군 재확인 |

## 23. 원화 기준 손익분기 모델

### 23.1 계산 변수

아래 모델은 실제 수익 예측이 아니라 트래픽 규모를 판단하기 위한 민감도 계산이다.

```text
I = Monthly Ad Impressions
C = Monthly Puzzle Completions
O = Ad Opportunity Rate
S = Ad Show Rate
E = eCPM in USD
F = KRW per USD
R = Gross Revenue in KRW
K = Monthly Operating Cost in KRW

I = C * O * S
R = I / 1,000 * E * F
Net Operating Contribution = R - K
Break-even Completions = K * 1,000 / (O * S * E * F)
```

### 23.2 예시 가정

- 광고 기회율 `O = 0.5`
- 실제 노출률 `S = 0.6`
- 완주당 실제 광고 노출 `0.3회`
- 환산 가정 `F = 1,400 KRW/USD`
- 광고 차감·세금·환전 수수료 전 총수익

`1 USD = 1,400 KRW`는 계산 설명용 고정 가정이며 실제 환율이 아니다. 사업 판단 시
정산일 환율과 실제 광고 보고서 값으로 교체한다.

| 월 완주 | 예상 노출 | `eCPM $2` | `eCPM $5` | `eCPM $10` |
|---:|---:|---:|---:|---:|
| 10,000 | 3,000 | 8,400원 | 21,000원 | 42,000원 |
| 50,000 | 15,000 | 42,000원 | 105,000원 | 210,000원 |
| 100,000 | 30,000 | 84,000원 | 210,000원 | 420,000원 |
| 500,000 | 150,000 | 420,000원 | 1,050,000원 | 2,100,000원 |

### 23.3 운영비별 손익분기 완주 수

같은 가정에서 광고 총수익만으로 월 운영비를 충당하려면 다음 완주량이 필요하다.

| 월 운영비 | `eCPM $2` | `eCPM $5` | `eCPM $10` |
|---:|---:|---:|---:|
| 10,000원 | 약 11,905회 | 약 4,762회 | 약 2,381회 |
| 50,000원 | 약 59,524회 | 약 23,810회 | 약 11,905회 |
| 100,000원 | 약 119,048회 | 약 47,619회 | 약 23,810회 |
| 500,000원 | 약 595,238회 | 약 238,095회 | 약 119,048회 |

운영비에는 다음을 포함한다.

- 독립 도메인과 인프라 비용
- Worker 초과 호출과 로그·모니터링 비용
- CMP 또는 개인정보 관리 비용
- 결제·환전·송금 수수료
- 세금과 회계 처리 비용
- 광고 검수, 장애 대응, 정책 관리에 투입한 시간 비용

광고 사업자의 보고 수익은 순이익이 아니다. 실제 손익표에는 직접 판매, 화이트라벨,
인쇄 상품 수익을 별도 열로 기록하고 광고 성과와 섞지 않는다.

## 24. SEO URL 운영 명세

### 24.1 현재 네 개 게임 URL

독립 도메인이 확정되기 전에는 canonical host를 임의로 기록하지 않는다. 배포 시에는
각 path를 최종 독립 도메인의 절대 URL로 변환한다.

| Path | 주 검색 의도 | `title` | `hreflang` 상대 | 색인 | 구조화 데이터 원칙 |
|---|---|---|---|---|---|
| `/` | 무료 온라인 스도쿠, 설치 없는 스도쿠 | `무료 온라인 스도쿠 게임 \| 난이도별 새 퍼즐` | `/en/` | 허용 | 실제 기능만 `VideoGame`·`SoftwareApplication` |
| `/en/` | free online sudoku, new sudoku puzzle | `Free Online Sudoku Game \| New Puzzle by Difficulty` | `/` | 허용 | 한국어 페이지와 같은 기능만 영어로 기술 |
| `/rush/` | 스도쿠 러시, 타임어택 스도쿠 | `스도쿠 러시 \| 무료 타임어택 스도쿠 게임` | `/en/rush/` | 허용 | 실제 시간제한·점수 기능만 기술 |
| `/en/rush/` | sudoku rush, timed sudoku | `Sudoku Rush \| Free Timed Sudoku Game` | `/rush/` | 허용 | 한국어 Rush와 같은 기능만 영어로 기술 |

모든 URL은 자기 참조 canonical을 사용하고 언어 쌍에 `ko`, `en`, 필요 시
`x-default`를 상호 연결한다. canonical과 `hreflang`은 redirect URL이 아니라 최종
HTTP `200` URL을 가리킨다.

### 24.2 기능형 URL의 색인 조건

| Path | 색인을 허용할 조건 | 색인을 보류할 조건 |
|---|---|---|
| `/daily-sudoku/` | 실제 날짜별 공통 퍼즐, 고유 상태와 공유 기능 제공 | 시드만 URL에 바꾸거나 기존 게임과 동일한 빈 셸 |
| `/printable-sudoku/` | 실제 다운로드 가능한 샘플 PDF와 정답 제공 | PDF나 고유 기능 없이 홍보 문구만 존재 |
| `/business/` | 제공 범위, 대상, 연락 방법이 실제로 준비됨 | 판매할 수 없는 기능·가격·인증을 기재 |

`/daily-sudoku/`를 구현할 경우 기존 랜덤 생성기로 퍼즐을 한 번 생성한 뒤 서버에
저장한다. URL 재현을 위한 생성 시드를 사용하지 않는다.

### 24.3 배포 검증표

- HTML 응답의 `title`, description, canonical, `hreflang`이 URL별로 고유하다.
- canonical은 절대 HTTPS URL이며 자기 자신을 가리킨다.
- sitemap에는 색인 허용 URL만 포함한다.
- `robots.txt`와 페이지의 robots meta가 서로 모순되지 않는다.
- 구조화 데이터의 이름, 언어, 기능, 가격은 화면과 실제 서비스에 존재한다.
- 평점·리뷰·다운로드 수를 임의로 생성하지 않는다.
- Open Graph 이미지가 HTTP `200`, 권장 공유 비율, 올바른 MIME type을 제공한다.
- favicon은 검색엔진 요구 형식과 크기를 충족한다.
- Search Console, Naver Search Advisor, Bing에서 대표 URL을 각각 검사한다.
- JavaScript 비활성 상태에서도 페이지 이름과 게임의 실제 목적을 식별할 수 있다.

  않는다.
- CSP는 필요한 사업자 출처만 허용하고 wildcard를 최소화한다.
- 광고 callback payload를 신뢰해 퍼즐 상태나 서버 권한을 변경하지 않는다.
- 보상은 동일 광고 기회에 한 번만 지급하고 재전송에 안전하게 처리한다.
- 오류 로그에 전체 URL query, 광고 식별자, 퍼즐 정답을 남기지 않는다.
- 개인정보 또는 계약 자료에 접근하는 운영 계정은 다중 인증을 사용한다.

### 26.3 기록 유지 규칙

- 정책·가격·승인 조건은 확인 날짜와 원문 URL을 함께 기록한다.
- 가정이 관측값으로 바뀌면 원래 가정을 삭제하지 않고 결과와 결정 날짜를 추가한다.
- 한 실험에서 빈도, placement, 형식을 동시에 바꾸지 않는다.
- 코드 배포, 광고 설정 변경, CMP 변경, 도메인 이전을 서로 다른 변경으로 기록한다.
- 수익은 광고 사업자 보고서, 지급 내역, 비용 증빙을 구분해 기록한다.
- 분기마다 외부 정책 링크와 사업자 조건의 유효성을 다시 확인한다.
