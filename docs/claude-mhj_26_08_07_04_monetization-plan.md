# 수익화 계획서

작성일: 2026-08-07 · 대상: 이 스도쿠 프로젝트 (`ui-composition-layer` / `bb0de56`)

---

## 0. 결론부터

**이 게임을 그대로 광고·구독으로 파는 경로는 기대수익이 사실상 0이다.**
스도쿠는 웹에서 가장 포화된 카테고리이고, 무료 대체재가 압도적으로 강하며,
이 프로젝트에는 트래픽을 확보할 경로가 없다. 이 문서에서 계산해 보였듯
광고로 월 10만 원을 벌려면 **월 5만 세션**이 필요한데, `.pages.dev`
서브도메인에 콘텐츠가 없는 상태에서 이 숫자에 도달할 현실적인 방법이 없다.

**대신 이 프로젝트에는 실제로 값이 나가는 자산이 세 개 있다** — 생성 엔진,
접근성 구현, 그리고 0에 수렴하는 운영비다. 셋 다 **최종 사용자가 아니라
다른 사업자에게** 값이 나간다. 따라서 계획의 방향은 B2C가 아니라 B2B다.

가장 정직한 평가를 하나 더 덧붙이면 (7절), 이 프로젝트의 최대 기대수익은
**제품 매출이 아니라 개발자 역량 증명으로서의 가치**일 가능성이 높다.

## 1. 자산 실사 — 무엇을 실제로 갖고 있나

추정이 아니라 코드와 측정으로 확인된 것만 적는다.

| 자산 | 근거 | 시장 가치 |
|---|---|---|
| DLX 생성 엔진 | 유일해 보장, 힌트 22~60개 지정, 생성 0.4~1.8ms(22개는 ~55ms) | **높음** — 개발자·출판사 대상 |
| 접근성 구현 | 대비 76쌍 자동 게이트, 전 기능 키보드 조작, `aria-live` 안내, 색 외 신호 병행, `innerHTML` 금지를 테스트로 강제 | **높음** — 조달 요건이 있는 시장 |
| 운영비 구조 | Worker 14.6KB, DB·상태 없음 | 중간 — 마진은 좋으나 그 자체로는 안 팔림 |
| 공유 링크 | URL에 진행상태 압축 인코딩 | 낮음 |
| 게임 자체 | 완성도 높은 단일 스도쿠 | **낮음** — 무료 대체재 과다 |

**결정적 제약 두 가지**

1. **한국어 전용** — 모든 문자열이 하드코딩된 한국어다. i18n 구조가 없다.
   해외 B2B/API 시장을 노리는 순간 이것이 첫 번째 장벽이 된다.
2. **판매 가능한 형태가 아님** — 인증, 사용량 계측, 요금 부과, 랜딩 페이지,
   문서가 전부 없다. 지금은 "제품"이 아니라 "잘 만든 앱"이다.

## 2. 비용 구조 — 유일하게 확실한 좋은 소식

Cloudflare Workers Paid 기준 (2026년 요금):

| 항목 | 포함량 | 초과 단가 |
|---|---|---|
| 기본료 | $5/월 | — |
| 요청 | 1,000만 건/월 | 100만 건당 $0.30 |
| CPU 시간 | 3,000만 ms/월 | 100만 ms당 $0.02 |

**측정값 대입** (이 세션 실측: 기본 32개 힌트 생성 ≈ 1ms, 평균 3ms 가정):

- 3,000만 ms ÷ 3ms = **월 1,000만 회 퍼즐 생성이 기본료에 포함**
- 정적 파일은 Pages가 무료·무제한 처리하므로 Worker 요청은 `/api/new-puzzle/`만 계산
- 세션당 3판을 가정하면 **월 330만 세션까지 $5**

즉 **현실적으로 도달 가능한 어떤 규모에서도 인프라 비용은 문제가 되지 않는다.**
이것은 진짜 강점이다. 다만 강점의 성격을 오해하면 안 된다 — 비용이 낮은 것이지
수익이 생기는 것이 아니다. 손익분기는 **월 $5**이고, 문제는 그 $5조차 광고로
벌기 어렵다는 데 있다.

## 3. 수익 모델별 분석

### 3.1 광고 (B2C)

**계산**: 이 앱은 SPA라 **방문당 페이지뷰가 1**이다. 페이지뷰 기반 RPM
모델에서 가장 불리한 구조다. 퍼즐/캐주얼 웹 디스플레이 광고 RPM을 $2로 잡으면:

| 목표 월수익 | 필요 월 세션 |
|---|---|
| $5 (손익분기) | 2,500 |
| $100 | 50,000 |
| $1,000 | 500,000 |

**병목은 수익화가 아니라 트래픽 확보다.** 스도쿠 검색 상위는
sudoku.com·NYT 등이 장악하고 있고, 신규 `.pages.dev` 도메인이 유입을 얻으려면
콘텐츠 마케팅이나 유료 광고가 필요하다. 유료 광고는 CPC가 광고 RPM을 초과하므로
구조적으로 적자다.

**판정: 주 수익원으로 부적합.** 트래픽이 이미 있다면 얹는 것은 합리적이나,
트래픽을 만들기 위해 광고를 도입하는 것은 순서가 거꾸로다.

### 3.2 구독 / 인앱 결제 (B2C)

무료로 완전히 동등한 대체재가 널려 있는 상태에서 일반 스도쿠에 대한 지불의사는
거의 0이다. 광고 제거·통계·테마 같은 전형적 상품은 **먼저 대규모 무료 사용자
기반이 있어야** 성립한다.

**판정: 단독으로는 비현실적.** 3.1의 트래픽 문제를 먼저 풀지 않으면 의미 없음.

### 3.3 앱스토어 배포

PWA 래핑 비용 자체는 낮지만, 스토어 검색(ASO)의 경쟁 강도는 웹 SEO와 동일하거나
더 심하다. 여기에 스토어 수수료, 심사, 플랫폼별 유지보수가 추가된다.

**판정: 발견 문제를 해결하지 못한 채 비용만 추가.** 다른 경로로 수요가 검증된
뒤에 고려할 것.

### 3.4 생성 엔진 API / 라이선스 (B2B)

엔진은 객관적으로 좋다 — 유일해 보장, 힌트 수 지정, 밀리초 단위 생성. 이를
필요로 하는 쪽은 **다른 개발자와 퍼즐 서비스**다.

- **형태**: 종량제 API, 또는 소스 라이선스 판매
- **필요한 것**: API 키 인증, 사용량 계측, 요금 청구, 영문 문서, 랜딩 페이지,
  안정성 약속(SLA)
- **경쟁**: 무료 오픈소스 생성기가 존재. 차별점은 **속도·유일해 보장·힌트 수
  제어**를 한꺼번에 제공하는 것과, 즉시 쓸 수 있는 호스팅 형태라는 점
- **규모 감각**: 시장이 작다. 월 수십~수백 달러 수준을 기대하는 것이 정직하다

**판정: 자산을 실제로 활용하는 첫 번째 현실적 경로. 다만 소규모.**

### 3.5 접근성을 무기로 한 B2B / 공공 (가장 방어 가능)

이 프로젝트의 접근성 수준은 개인 프로젝트에서 드물다 — **자동화된 대비 검증
게이트가 테스트에 박혀 있고**, 전 기능이 키보드로 조작되며, 상태 변화가
`aria-live`로 안내되고, 모든 시각 신호가 색 외 수단과 병행된다.

핵심은 이것이 **취향이 아니라 조달 요건인 시장이 있다**는 점이다:

- 공공기관·교육기관 웹서비스 (접근성 준수가 법·계약 요건)
- 도서관·복지관·시니어 대상 디지털 프로그램
- 인지 재활·치매 예방 프로그램 (스도쿠는 이 영역의 표준 도구)

이 시장의 구매자는 **스도쿠가 아니라 "규정을 통과하는 스도쿠"에 돈을 낸다.**
경쟁자 대부분은 접근성이 형편없으므로 실질 경쟁이 적다.

- **필요한 것**: 접근성 준수 보고서(VPAT/한국형 웹 접근성 인증 검토),
  납품 가능한 형태(임베드 위젯/설치형), 사업자 등록, 레퍼런스 1건
- **규모 감각**: 건당 수백만 원 규모의 용역·납품이 가능한 영역. 건수는 적지만
  단가가 광고와 비교가 안 됨

**판정: 가장 방어 가능하고 단가가 높은 경로. 자산과 시장이 정확히 맞물린다.**

### 3.6 인쇄·출판용 퍼즐 공급

퍼즐책·신문·잡지·학습지는 **난이도 지정 + 유일해 보장 + 대량**의 퍼즐을
필요로 한다. 방금 만든 힌트 수 지정 기능이 정확히 이 요구에 대응한다.

- **필요한 것**: 대량 배치 생성, 인쇄 품질 출력(PDF/벡터), 힌트 수를 넘어선
  난이도 등급(사람이 푸는 난이도는 힌트 수와 정확히 비례하지 않음), 중복 방지
- **경쟁**: 이미 공급업체가 존재하나, 소규모·맞춤 물량은 진입 여지가 있음
- **규모 감각**: 소액이지만 **반복 매출**이 되기 쉬움

**판정: 화려하지 않지만 현실적. 3.5와 병행 가능.**

### 3.7 오픈소스 + 후원

코드 품질과 DLX 이식 과정은 교육적 가치가 있다. 다만 이런 규모의 프로젝트에서
GitHub Sponsors 수입은 통상 무시할 수준이다.

**판정: 수익원이 아님. 다만 3.4~3.6의 신뢰 자산으로는 유효.**

## 5. 단계별 실행 계획

각 단계 끝에 **중단 판단 기준**을 둔다. 반응이 없으면 다음 단계로 가지 않는다.

### 0단계 — 검증 없이 선행할 것 (비용 거의 0)

이미 진행한 SEO 작업의 결과를 관측할 기반을 만든다. **이 단계의 목적은 수익이
아니라 "수요가 존재하는가"의 데이터 확보다.**

- Google Search Console 등록, 사이트맵 제출
- 최소한의 분석 도구 도입 (Cloudflare Web Analytics — 무료, 쿠키 없음)
- 커스텀 도메인 확보 (연 1~2만 원). `.pages.dev`로는 어떤 B2B 대화도 어렵다

**판단 기준**: 3개월 후 자연 유입이 월 1,000 세션에 못 미치면 B2C 경로는
완전히 접는다.

### 1단계 — 자산을 판매 가능한 형태로 (1~2개월)

3.5와 3.6 어느 쪽으로 가든 공통으로 필요하다.

- **영문 i18n 구조 도입** — 지금 문자열이 하드코딩되어 있어 나중에 할수록 비싸진다
- 접근성 준수 근거 문서화 — 이미 자동 검증이 있으므로 **결과를 정리하는 수준**
- 엔진을 임베드 가능한 형태로 분리 (현재 Worker에 묶여 있음)

### 2단계 — 시장 하나만 골라 타진 (2~3개월)

**두 시장을 동시에 하지 말 것.** 3.5(접근성 B2B)를 우선 권한다 — 단가가 높고
경쟁이 적으며 자산 적합도가 가장 높다.

- 데모 페이지 1개 + 접근성 근거 자료로 10~20곳 접촉
- 목표는 매출이 아니라 **"이 요구가 실재하는가"의 확인**

**판단 기준**: 20곳 접촉에 유의미한 회신이 0이면 3.6으로 전환한다.

### 3단계 — 검증된 것만 제품화

수요가 확인된 하나에만 인증·계측·청구·계약 등 실제 비용을 투입한다.

## 6. 하지 말아야 할 것

- **트래픽이 없는 상태에서 광고부터 붙이기** — 수익은 0인데 사용자 경험과
  성능(이 프로젝트의 강점)만 훼손된다
- **여러 수익 모델 동시 추진** — 1인 프로젝트에서 가장 흔한 실패 원인
- **경쟁사 기능 따라잡기** — 기능 수로는 절대 이기지 못한다. 이길 수 있는
  축(접근성·생성 품질)에만 투자할 것
- **"스도쿠" 일반 검색 상위를 목표로 삼기** — 도메인 권위가 지배하는 영역이라
  개인이 뒤집기 어렵다
- **수익화를 위해 코드 품질을 희생하기** — 이 프로젝트에서 팔 수 있는 것이
  정확히 그 품질이다

## 7. 가장 정직한 평가

위 계획을 모두 실행해도 **이 프로젝트가 생활을 지탱할 매출을 낼 확률은 낮다.**
스도쿠라는 소재 자체가 그렇다.

반면 이 코드베이스가 증명하는 것들 — DLX를 이식하며 **측정으로 결정한 기록**
(2,000회 굴착으로 하한 21을 확인하고 17이 불가능함을 논증한 과정), 접근성을
테스트로 강제하는 습관, 단계별 설계 승인 절차, 커밋 하나하나의 근거 서술 — 은
채용·컨설팅·기술 신뢰도 측면에서 **직접 매출보다 큰 기대값**을 가질 가능성이
높다.

따라서 권고는 다음과 같다:

> **이 프로젝트를 매출 사업으로 밀어붙이기 전에, 포트폴리오 자산으로서 먼저
> 회수하라.** DLX 이식 과정과 접근성 구현을 기술 글로 공개하는 것이,
> 3.4~3.6의 신뢰 기반을 만들면서 동시에 가장 큰 기대값을 갖는 단일 행동이다.

그 위에서 3.5(접근성 B2B)를 소규모로 타진하는 것이 자산을 낭비하지 않는
순서다.

## 8. 이 문서의 한계

- 광고 RPM $2, 세션당 3판 등은 **업계 통상치를 사용한 가정**이며 이 사이트의
  실측이 아니다. 0단계에서 실제 데이터로 대체해야 한다
