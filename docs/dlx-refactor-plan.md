## 1. 진단 (개선 전 실측)

### 1.1 12×12는 동작하지 않았다

`generator._box_constraint()`가 `sqrt(dim)`에 의존했다. 12는 완전제곱수가 아니므로 박스 분할이 깨진다.

| dim | 박스 제약 열 수 | 기대값 | 최대 인덱스 | 행렬 열 수 | 결과 |
|-----|----------------|--------|------------|-----------|------|
| 9   | 81             | 81     | 323        | 324       | 정상 |
| 12  | **176**        | 144    | **608**    | **576**   | **AssertionError** |
| 16  | 256            | 256    | 1023       | 1024      | 정상 (float 경유) |

12×12의 박스는 정사각형이 아니라 **가로 4 × 세로 3**이다. `sqrt` 공식으로는 표현할 수 없다.

### 1.2 판정 시간의 절반이 "행렬 구축"이었다

`has_unique_solution()`이 호출될 때마다 행렬을 처음부터 다시 지었다.

| dim | givens | 전체 | 행렬 구축 | 탐색 |
|-----|--------|------|----------|------|
| 9   | 32     | 4.3ms | 2.2ms (50.3%) | 2.2ms (49.7%) |
| 16  | 120    | 31.1ms | 15.3ms (49.2%) | 15.8ms (50.8%) |

### 1.3 병목은 알고리즘이 아니라 객체·제너레이터 오버헤드였다

`cProfile` 상위 (9×9 판정 20회):

```

  1680    0.022   dlx.py:36(select_min_col)
```

## 2. 설계

### 2.1 크기 파라미터화 — `SudokuSpec`

`sqrt` 대신 박스의 가로/세로를 **명시적으로** 보유한다. (`game/sudoku/spec.py`)

```
SudokuSpec(dim, box_w, box_h)      불변식: box_w * box_h == dim
  9 -> 3x3      12 -> 4x3      16 -> 4x4      6 -> 3x2
```

제약 열은 float 없이 (행, 열, 값) 삼중쌍에서 직접 계산한다.

```
box   = (r // box_h) * (dim // box_w) + (c // box_w)
열 4개: r*dim+c │ dim²+r*dim+v │ 2dim²+c*dim+v │ 3dim²+box*dim+v
```

`SudokuSpec.for_dim()`은 임의의 dim에 대해 가장 정사각형에 가까운 박스를 고른다. 9/12/16 외 크기도 자동 지원된다.

### 2.2 배열 기반 DLX

노드를 객체가 아닌 **정수 인덱스**로 표현하고 6개 병렬 리스트를 쓴다. (`game/sudoku/dlx.py`)

```
이전:  node.right.up          객체 역참조 + 제너레이터
이후:  U[R[i]]                리스트 인덱싱
```

후보 행마다 제약이 항상 4개이므로 **노드 총량이 사전에 확정**된다 (`1 + 4·dim² + 4·dim³`). 전량 미리 할당하고, 행을 순서대로 채우면 열 맨 아래 O(1) 추가가 되어 **`insert_node`의 선형 스캔이 사라진다.**

| dim | 행 | 열 | 노드 총수 |
|-----|----|----|----------|
| 9   | 729 | 324 | 3,241 |
| 12  | 1,728 | 576 | 7,489 |
| 16  | 4,096 | 1,024 | 17,409 |

**`array('i')`가 아니라 `list`를 쓴다.** 실측 결과 `array('i')`가 오히려 40% 느렸다 (300만 회 인덱스 추적에서 56.1ms vs 40.0ms). 인덱스가 CPython의 small-int 캐시(−5..256)를 한참 넘어서 읽을 때마다 int 객체를 새로 만들기 때문이다.

### 2.3 비재귀 탐색 엔진

재귀를 **3상태 기계 + 명시적 스택**으로 대체했다.

```
stack_col[d]     해당 깊이에서 선택한 열
stack_node[d]    그 열에서 현재 시도 중인 후보 노드
stack_start[d]   그 열의 스캔을 시작한 지점 (무작위화용)

DESCEND    행렬이 비면 해 발견. 아니면 MRV로 열 선택 → cover → ADVANCE
ADVANCE    직전 후보를 되돌리고 다음 후보로. 소진되면 uncover → BACKTRACK
BACKTRACK  depth-1. 0 미만이면 종료. 아니면 ADVANCE
```

요구사항 대응:

- **현재 탐색 노드 위치 기억** → `stack_node[depth]`가 그 자체로 위치
- **실패 시 다음 시도 노드로 복귀** → `ADVANCE`가 되돌리기와 다음 후보 이동을 함께 처리
- **재귀 없음** → 단일 `while` 루프. `sys.setrecursionlimit(60)`으로도 16×16이 풀린다 (테스트로 고정)

무작위화는 각 열의 후보 스캔을 임의 지점에서 시작해 순환시키는 방식이다. 첫 선택은 균등하면서 백트래킹 시 모든 후보에 여전히 도달한다 (테스트로 고정).

### 2.4 반복 예산

크기별 최대 반복 횟수를 둔다. 다만 **중앙값이 아니라 꼬리 기준**으로 잡아야 한다. 크기별 200회 판정 실측:

| size | median | p95 | max | budget | 여유 | 최악 1회 소요 |
|------|--------|-----|-----|--------|------|--------------|
| 9×9 | 146 | 253 | 404 | 200,000 | 495배 | 0.2s |
| 12×12 | 251 | 738 | 2,218 | 1,000,000 | 451배 | 0.9s |
| 16×16 | 921 | 20,878 | **185,264** | 5,000,000 | 27배 | 4.7s |

16×16의 최대값은 중앙값의 **201배**다. 예산을 `dim³`(4096) 같은 값으로 잡았다면 정상 퍼즐도 계속 중단됐을 것이다.

엔진은 초당 약 **1.07M 반복**을 처리하므로, 위 예산은 판정 1회를 각각 0.2s / 0.9s / 4.7s로 제한한다. 도달하라고 만든 값이 아니라 최악의 경우를 유한하게 만드는 값이다.

**예산 초과는 보수적으로 처리한다.** `Uniqueness.BUDGET_EXCEEDED`는 `UNIQUE`/`MULTIPLE`/`NO_SOLUTION`과 구분되는 별도 값이며, 구멍 파기 중 발생하면 그 칸을 되돌린다. 따라서 예산은 **난이도에만 영향을 주고 정답성에는 영향이 없다.** 실측:

| budget | 결과 단서 수 | 해의 개수 |
|--------|-------------|----------|
| 1 | 40, 49, 41, 42, 42, 43 | 전부 1 |
| 10 | 33, 42, 29, 32, 29, 40 | 전부 1 |
| 100 | 29, 27, 26, 25, 27, 26 | 전부 1 |
| 기본값 | 26, 26, 25, 25, 25, 25 | 전부 1 |

예산을 굶길수록 퍼즐이 쉬워질 뿐, **유일해는 항상 유지된다.**

### 2.5 유일해 판정 고속화

**(a) 행렬 1회 구축 후 재사용** — 크기별 행렬을 한 번 만들고, 판정 시 단서에 해당하는 열만 `cover`한 뒤 역순으로 `uncover`한다. 컨텍스트 매니저(`matrix.givens(board)`)로 감싸 예외가 나도 반드시 복구된다. 판정 비용이 `O(dim³)` 삽입에서 `O(givens × 4)` cover로 바뀐다. **이것이 가장 큰 이득이었다.**

**(b) 표적 유일성 검사** — 구멍 파기 시, 값 `v`를 지운 칸은 원래 해가 항상 존재하므로 비유일해가 되는 경우는 **그 칸이 다른 값을 가질 수 있을 때뿐**이다. 따라서 합법인 `w ≠ v`만 고정해 해 1개를 찾아본다.

> 전제 조건: 직전 보드가 유일해임이 이미 알려져 있어야 한다. 구멍 파기는 이 불변식을 귀납적으로 유지하므로 성립한다. 전제가 없는 외부 호출은 `classify()`를 써야 한다. (`solver.alternative_exists` docstring에 명시)

측정 결과 **1.1x / 1.2x / 1.4x**로 이득이 크지 않았다. 단서 수는 두 방식이 동일했다. 대안보다 복잡하지 않아 채택했지만, 큰 이득은 (a)와 2.2절에서 나왔다.

**(c) MRV 조기 종료** — 열 크기가 1이면 더 나은 후보가 없으므로 즉시 스캔을 중단한다.

**(d) 채택하지 않은 것** — 제약 전파 선처리, MRV 자료구조 개선. 생성 속도가 이미 충분하고(9×9 hard 0.059s, 16×16 hard 1.25s) 측정된 필요가 없어 복잡도만 늘어난다.

### 2.6 스레드 안전성

탐색은 링크를 **제자리에서 변경**한다. 하나의 행렬을 Django 워커 스레드가 공유하면 서로의 상태를 망가뜨린다. 따라서 행렬 캐시는 `threading.local()` 기반이다. 스레드당 최초 1회 구축 비용(16×16 약 30ms)만 들고 이후는 무료다. (동시성 테스트로 고정)

## 4. 테스트

74개, 2.6초. `python manage.py test game`

| 층위 | 내용 |
|------|------|
| 기하 | 세 크기 모두 제약 열 4계열이 정확히 `dim²`개, 박스가 균등 분할 |
| 불변식 | `cover`→`uncover` 후 링크 상태가 바이트 단위로 동일 |
| 불변식 | 탐색 종료 후 행렬이 초기 상태와 동일 (정상·예산초과·예외 발생 모두) |
| 대조 | 독립 오라클과 해의 개수 일치 (9×9 40판, 12×12 5판) |
| 속성 | 생성된 퍼즐이 **오라클 기준** 정확히 1개의 해 (엔진 자신이 아니라) |
| 속성 | 모든 예산에서 유일해 유지, 예산이 작을수록 단서가 많아짐 |
| 비재귀 | `setrecursionlimit(60)`에서 16×16 풀이 성공 |
| 동시성 | 스레드별 행렬 분리, 4스레드 동시 풀이 결과 안정 |
| 하위호환 | 기존 `generator` API 및 두 뷰 엔드포인트 동작 |

**오라클은 DLX와 코드를 공유하지 않는다.** 비트마스크 백트래킹으로 별도 구현했으며 재귀를 쓴다. 구조가 다른 것이 요점이다 — exact-cover 기계를 재사용한 오라클은 exact-cover 기계의 버그를 잡을 수 없다.

### 개발 중 발견한 버그 하나

예산 초과 시 행렬이 복구되지 않는 버그가 있었다. `ADVANCE` 상태에서 예산이 소진되면 깊이 `depth`의 열이 이미 covered인데 `depth-1`까지만 되감아 열 하나가 covered로 남았다. 스레드로컬 캐시가 오염되어 이후 탐색이 **무한 루프**에 빠졌다 (전체 테스트가 멈추는 것으로 나타남).

최초 테스트는 예산 하나(=5)만 시험해서 dim=9는 우연히 통과했다. 지금은 예산을 1~120까지 훑어 세 상태를 모두 지나가게 한다. 단일 값 테스트로는 상태 기계를 검증할 수 없다는 교훈.

## 5. 남은 범위 (이번에 하지 않음)

Phase 7은 명시적으로 제외했다. 알고리즘 계층은 12×12·16×16 퍼즐을 **생성**하지만, 화면에서 플레이하려면 아래가 필요하다.

- `game/static/game/css/style.css:27-28` — `repeat(9, 40px)` 하드코딩
- `game/static/game/js/game.js:19-20` — `Math.floor(i / 9)`, `i % 9`
- `game/static/game/js/game.js:29` — `[^1-9]` (10 이상 입력 불가)
- `game/views.py` — `dim` 파라미터 없음

추가 고려사항:

- **16×16 표기** — 백엔드는 항상 정수 `1..dim`(0=빈칸)이다. 표시 문자(`A`~`G` 등) 매핑이 필요하면 프론트에서 하는 편이 API를 크기와 무관하게 유지한다.
- **사전 생성 캐시** — 16×16 hard가 1.25s이므로 요청-응답 안에서 처리하기엔 부담이다. `models.py`가 비어 있어 `Puzzle` 모델 + 관리 커맨드를 넣기 좋은 상태다.
- **버전 관리** — 이 프로젝트는 git 저장소가 아니다. `git init`을 권한다.
