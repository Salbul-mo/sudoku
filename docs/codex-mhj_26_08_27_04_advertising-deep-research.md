# 스도쿠 광고 수익화 심층 연구

- 작성일: 2026-08-27
- 조사 기준일: 2026-08-27
- 대상: `sudoku-bw7.pages.dev`의 Classic·Rush 한국어/영어 웹 게임
- 범위: 광고 상품, 승인, 배치, 개인정보, 검색 영향, 성능, 수익 민감도,
  구현 지점, 실험·중단 기준

이 문서는 광고 도입을 승인하거나 실제 매출을 예측하는 문서가 아니다. 공식 정책과
현재 저장소를 근거로 광고 도입 가능성, 선행 조건, 검증 방법을 정리한다. 법률·세무
판단은 관할 전문가 검토를 대체하지 않는다.

---

## 0. 결론

현재 프로젝트에 가장 적합한 광고 상품은 **Google AdSense H5 Games Ads의
완료 후 `Interstitial`**이다. 광고를 자체 `DialogHost`에 삽입하는 방법은 권장하지
않는다. 기존 모달이 닫힌 뒤 사용자가 `새 게임` 또는 `다시 하기`를 선택한 자연스러운
전환 지점에서 Google의 `Ad Placement API`가 전체 화면 광고를 관리하게 해야 한다.

다만 지금 바로 광고 코드를 배포하는 순서는 현실적이지 않다.

1. 독립 도메인·개인정보처리방침·지역별 동의 체계를 먼저 준비한다.
2. 검색·방문·완주·재시작의 무광고 기준 데이터를 확보한다.
3. 일반 AdSense 사이트 승인을 받는다.
4. 별도 신청형인 H5 Games Ads 승인을 받는다.
5. 테스트 광고로 실패·차단·무재고 경로를 검증한다.
6. Rush 트래픽 일부에서 완료 후 광고를 먼저 실험한다.
7. 실제 `eCPM`, 광고 노출률, 재시작률, 재방문율로 계속할지 결정한다.

Google은 H5 Games Ads의 트래픽 최소치를 공개하지 않는다. 일반 AdSense도 공식적인
최소 방문자 수를 제시하지 않지만, 충분한 고유 콘텐츠와 좋은 탐색 경험을 요구한다.
현재 사이트는 네 개의 앱 셸 페이지로 구성돼 있어 일반 사이트 심사에서 콘텐츠가
부족하다고 판단될 위험이 있다. 또한 H5 Games Ads는 신청형 상품이고 승인이 보장되지
않는다.

### 한 문장 권고

> 광고 승인을 받기 전에는 구현하지 않고, 승인 후에는 Rush의 `다시 하기`에
> 10분 빈도 제한을 둔 H5 전면 광고를 10% 트래픽부터 시험한다.

## 1. 사실·가정·미확인 항목

| 구분 | 내용 |
|---|---|
| 확인된 사실 | 현재 광고 SDK, 광고 단위, 분석 비콘, CMP, 개인정보처리방침, `ads.txt`가 없다. |

`pages.dev` 등록 가능성과 실제 사이트/H5 승인은 다른 문제다. 독립 도메인이 없어도
신청을 시도할 수 있다는 뜻이지 승인 가능성이 높다는 뜻은 아니다. 장기 브랜드,
`ads.txt`, 사이트 이전, 직접 광고 영업까지 고려하면 독립 도메인을 먼저 연결하는
편이 안전하다.

## 2. 현재 구현과 광고의 접점

### 2.1 Classic

Classic의 현재 흐름은 다음과 같다.

1. `store.subscribe()`가 `store.isSolved()`를 관찰한다.
2. 처음 완성 상태가 되면 접근성 알림을 보낸다.
3. 사용자가 `새 게임`을 선택하면 난이도 모달을 연다.
4. 난이도 선택이 확정되면 `deps.startNewGame()`을 호출한다.
5. `restart()`가 새 퍼즐을 요청하고 현재 보드를 교체한다.

광고 삽입 후보는 난이도 선택 완료와 `deps.startNewGame()` 사이이다. 그러나 미완성
게임을 버리는 사용자에게까지 전면 광고를 표시하면 자연스러운 완료 지점이라는
근거가 약해진다. 따라서 세션에 `completed` 상태를 기록하고, 완료된 퍼즐 뒤의 새
게임에서만 광고 기회를 선언해야 한다.

### 2.2 Rush

Rush의 현재 흐름은 광고에 더 적합하다.

1. 점수 상태가 종료 조건에 도달한다.
2. `gameOver()`가 타이머와 입력을 중지한다.
3. 결과 패널에 점수·최고 콤보·`다시 하기` 버튼이 나타난다.
4. `다시 하기`가 `game.start()`를 호출한다.
5. `puzzle-source`는 다음 보드를 미리 준비한다.

광고 삽입 후보는 `다시 하기` 클릭과 `game.start()` 사이이다. 게임이 이미 중지됐고,
사용자가 다음 게임 의사를 명시했으므로 가장 명확한 자연 전환 지점이다.

### 2.3 기존 모달의 제약

현재 `DialogHost`는 다음 속성을 가진다.

- 동시에 하나의 모달만 허용
- 배경 요소에 `inert` 적용
- `role="dialog"`와 `aria-modal="true"` 적용
- 모달 내부 포커스 순환
- 종료 후 이전 포커스 복원

일반 AdSense 단위를 이 DOM 모달 안에 직접 넣으면 광고 닫기 버튼, 외부 iframe,
포커스 트랩, 배경 `inert`가 충돌할 수 있다. 난이도·재시작 버튼과 광고가 가까워져
우발 클릭 위험도 커진다. 기존 모달은 먼저 닫고 H5 Games Ads가 자체 전체 화면을
표시하도록 분리해야 한다.

## 3. 광고 상품 비교

| 상품 | 현재 적합도 | 장점 | 핵심 제약 | 권고 |
|---|---:|---|---|---|
| AdSense H5 `Interstitial` | 높음 | 게임 완료 지점 제어, 전체 화면, API 빈도 관리 | 일반 AdSense와 H5 별도 승인 | Rush부터 실험 |
| AdSense H5 `Rewarded` | 중간 | 명시적 동의, 사용자 반감 감소 | 실제 보상 설계와 지급 보장 필요 | 수요 확인 후 |
| Auto Ads `Vignette` | 낮음 | 코드가 단순하고 빈도 설정 가능 | 페이지 이동 중심, 추가 트리거 예측성 낮음 | 게임 페이지 제외 |
| 일반 디스플레이 광고 | 낮음 | 일반 AdSense만으로 가능 | 게임과 150px 거리 권고, UI 공간 필요 | 별도 콘텐츠 페이지만 |
| Anchor·Side rail | 낮음 | 레이아웃 공간을 덜 차지함 | 게임 조작과 시야 방해, 모바일 위험 | 초기 제외 |
| Google Ad Manager H5 | 낮음 | 더 정교한 재고·직접 판매·실험 | 운영 복잡도와 계약·수요 필요 | 대규모 이후 |
| 직접 스폰서 결과 카드 | 중간 | 광고 SDK·경매 의존 없음, 고정 계약 가능 | 직접 영업·표시 의무·소재 검수 | 기관 제휴 시 가능 |
| CrazyGames 배포 | 중간 | 자체 유입과 게임 광고 SDK | Basic Launch는 수익 없음, 플랫폼 기준 통과 필요 | Rush 채널 실험 |
| Poki 배포 | 낮음~중간 | 큐레이션·유입·광고 운영 | 선별, 계약, 웹 독점 조건 가능 | 계약 검토 후 |

### 3.1 H5 Games Ads

Google 공식 H5 상품은 두 형식을 제공한다.

- `Interstitial`: 레벨·라운드 사이 자연스러운 휴지 구간의 전체 화면 광고
- `Rewarded`: 광고 시청에 동의한 사용자에게 플랫폼 내부 보상을 제공하는 광고

`adBreak()` 호출은 광고 표시 명령이 아니라 **광고 기회 선언**이다. 실제 표시는
다음에 따라 달라진다.

- 배치 유형
- 앞선 사용자 동작
- 광고 재고
- 사용자의 개인정보·동의 설정
- 최근 광고 노출 횟수
- 태그와 AdSense의 빈도 설정

따라서 광고가 나오지 않는 경로는 정상 동작이며, 게임은 항상 계속되어야 한다.

H5 태그의 `data-ad-frequency-hint`는 평균 최소 간격을 초 단위로 전달한다. 서버
설정이 이를 무시하거나 덮어쓸 수 있으므로 절대 보장이 아니다. 본 프로젝트의 초기
실험값은 `600s`가 적절하다.

### 3.2 Auto Ads Vignette

Vignette는 페이지 사이에 나타나는 건너뛸 수 있는 전체 화면 광고다. 기본적으로
사용자가 사이트 내부 링크를 클릭해 페이지를 이동할 때 동작한다. 2026년에는 탭
복귀, 비활성 후 상호작용, 뒤로 가기 등의 추가 트리거도 제공되며 별도로 끌 수 있다.

현재 Classic은 새 퍼즐을 API로 교체하고 페이지를 이동하지 않는다. 따라서 기본
Vignette는 `새 게임`과 정확히 결합되지 않는다. 추가 트리거를 허용하면 사용자가
퍼즐을 푸는 도중 탭으로 돌아오거나 비활성 후 첫 입력에서 광고가 나타날 수 있어
게임 정책과 경험에 맞지 않는다.

결론적으로 Vignette는 블로그·인쇄 페이지가 생길 경우 해당 페이지 간 이동에서
검토할 수 있지만, Classic과 Rush 게임 페이지에는 적용하지 않는 편이 안전하다.

### 3.3 일반 디스플레이 광고

Google은 게임 조작 영역과 AdSense for Content 광고를 최소 150px 떨어뜨릴 것을
강하게 권고한다. 현재 화면은 보드와 조작부가 핵심 공간 대부분을 사용하므로 이
간격을 확보하면 다음 중 하나가 필요하다.

- 보드 아래로 긴 여백과 광고 슬롯 추가
- 데스크톱 측면 공간 확대
- 모바일에서 광고 때문에 추가 스크롤 발생

이는 UI 비변경 목표와 충돌한다. 일반 광고를 쓰려면 게임이 아닌 `/printable-sudoku/`
같은 별도 콘텐츠 페이지에 제한하는 편이 낫다.

### 3.4 보상형 광고

가능한 보상은 다음과 같다.

- Classic 힌트 1회
- Rush 생명 1개
- Rush 제한시간 추가
- 로컬 통계 테마 또는 비경쟁적 장식 해제

Google 정책상 보상은 플랫폼 내부에서만 사용되고 양도할 수 없어야 한다. 사용자는
광고 표시 전 행동과 보상을 명확하게 알아야 하며 적극적으로 동의해야 한다. 거절이나
중도 종료가 일반 게임 이용을 막아서는 안 되고, 끝까지 본 경우 약속한 보상을 반드시
제공해야 한다.

현재 Classic에는 설명형 힌트나 보상 경제가 없다. 광고를 위해 불필요한 보상 기능을
먼저 만드는 것은 범위가 뒤집힌다. Rush의 `추가 생명`이 제품적으로 필요하다는
사용자 근거가 생길 때만 보상형을 추가한다.

### 3.5 직접 스폰서

프로그램매틱 광고 승인이 실패하더라도 결과 화면에 직접 계약한 스폰서 카드를 표시할
수 있다. 이 경우 Google 광고 코드를 사용하지 않으므로 H5 승인에는 의존하지 않는다.

권장 형태:

- 결과 화면 아래 별도의 `광고` 또는 `후원` 표시
- 이미지 한 장, 한 문장, 명확한 외부 링크
- 자동 재생 영상 없음
- 닫기를 게임 진행 조건으로 만들지 않음
- 노출·클릭을 수집한다면 개인정보처리방침에 정확히 공개

장점은 낮은 트래픽에서도 고정 계약이 가능하다는 점이다. 단점은 광고주를 직접 찾아야
한다는 점이다. 시니어·교육·퍼즐 출판 등 게임과 관련된 B2B 고객이 생겼을 때 함께
제안하는 방식이 현실적이다.

### 3.6 게임 포털

자체 검색 유입과 별개로 게임 포털에 Rush를 배포하면 포털 트래픽으로 광고 재고를
만들 수 있다.

#### CrazyGames

- Basic Launch는 7~21일 동안 진행된다.
- 최소 7일과 500 plays를 모두 충족하면 평가할 수 있다.
- Basic Launch에서는 광고와 수익화가 비활성화된다.
- Full Launch에 진입해야 SDK 광고와 수익 배분이 활성화된다.
- 공식 가이드는 좋은 게임의 참고값으로 평균 플레이 10분 이상, D1 유지율 10~15%,
  1분 이상 플레이 전환율 80% 이상을 제시한다. 이는 모든 게임의 보장된 합격선이
  아니라 성과 참고값이다.
- 외부 광고는 허용되지 않고 CrazyGames SDK 광고만 사용해야 한다.

Rush는 짧은 반복 플레이와 점수 구조가 있어 Classic보다 포털 적합도가 높다. 다만
현재 장기 진행·일일 목표·메타 진행이 약해 D1 유지율이 관건이다.

#### Poki

- 큐레이션과 최종 심사를 거친다.
- 공식 문서는 웹 독점 계약을 선호하며 기본 계약기간을 5년의 참고값으로 설명한다.
- Poki가 유입한 사용자의 광고 수익은 공식 설명상 50:50이며, 직접 검색·북마크·자체
  커뮤니티 유입은 개발자에게 100%라고 안내한다.
- 비독점 계약은 수익 배분 대신 일회성 라이선스가 될 수 있다.
- 실제 조건은 개별 계약이 우선한다.

이미 자체 웹사이트를 운영하고 다른 포털에도 배포하려면 웹 독점 조항의 범위를
반드시 계약서에서 확인해야 한다. Poki는 첫 광고 실험보다 별도 유통 전략에 가깝다.

## 4. 승인 가능성과 선행 조건

### 4.1 일반 AdSense 사이트 승인

H5 Games Ads 전에 일반 AdSense 사이트가 `Ready` 상태여야 한다. Google의 공식
검토 항목은 다음을 포함한다.

- 사이트 소유 확인
- 페이지 접근 가능성과 HTTPS
- 정책 준수
- 충분한 고유 콘텐츠
- 좋은 사용자 경험
- 명확한 탐색 구조

Google은 최소 게시물 수나 최소 방문자 수를 공식적으로 정하지 않는다. 반면 “충분한
고유 콘텐츠”라는 정성 기준은 존재한다. 현재 네 개 페이지가 모두 게임 앱 셸이므로
실제 게임의 독창성과 별개로 자동·수동 심사에서 콘텐츠 부족으로 판단될 위험이 있다.

설명문을 게임 화면에 추가하지 않는 조건을 유지하려면 승인 전 다음 기능형 페이지를
고려한다.

- `/privacy/`: 실제 개인정보·광고·쿠키 처리 내용
- `/daily-sudoku/`: 저장된 당일 공통 퍼즐
- `/printable-sudoku/`: 실제 샘플 퍼즐과 정답 PDF
- `/about/` 또는 `/business/`: 운영 주체와 문의·라이선스 정보

단순 승인용 글을 대량 생성하면 안 된다. 실제 사용 가치와 탐색 기능이 있어야 한다.

### 4.2 H5 Games Ads 승인

H5 Games Ads는 별도 신청형이며 파트너 적격성에 따라 거절될 수 있다. 공개 문서에는
정확한 트래픽·완주 수 기준이 없다. 따라서 “월 몇 명이면 승인”이라는 수치를 만들면
안 된다.

신청 전 준비 근거:

- 실제 플레이 가능한 Classic·Rush
- 모바일·데스크톱 대응
- 자연스러운 광고 중단 지점
- 게임 완료·재시작 흐름
- 접근성 및 오류 처리
- 충분한 실제 이용자와 반복 플레이 데이터
- 개인정보·동의 체계

DOM 기반 스도쿠가 H5 게임으로 인정될지는 공개 문서만으로 확정할 수 없다. Google
문서는 H5 게임이 JavaScript로 구현되고 `canvas`는 “일반적으로” 사용된다고 설명할
뿐 필수라고 단정하지 않는다. 최종 판단은 신청 심사 결과로 확인해야 한다.

### 4.3 도메인

2026-08-27 Public Suffix List 원본에서 `pages.dev` 항목을 확인했다. AdSense는 Public
Suffix List에 있는 플랫폼의 하위 사이트를 사이트로 추가할 수 있다고 설명한다.
따라서 `sudoku-bw7.pages.dev` 등록을 기술적으로 배제할 근거는 없다.

그러나 다음 이유로 독립 도메인을 권고한다.

- 광고 계정과 사이트 소유권의 장기 일관성
- 루트 `ads.txt` 제어
- 검색 canonical과 브랜드 주소 통합
- 직접 스폰서·B2B 신뢰
- 플랫폼 이전 시 광고·검색 자산 보존

독립 도메인을 연결하면 `pages.dev`는 독립 도메인으로 리다이렉트하고 canonical,
sitemap, AdSense 사이트 등록을 새 도메인으로 통일한다.

## 5. 광고 정책상 허용·금지 경계

### 5.1 허용 가능성이 높은 흐름

- 결과 화면을 사용자가 충분히 확인한 뒤 `다시 하기`를 클릭
- 완성된 Classic에서 `새 게임`과 난이도를 선택
- 게임을 중지하고 입력을 비활성화한 상태에서 H5 API 호출
- 광고가 없으면 즉시 다음 게임 진행
- 사용자가 광고를 닫을 수 있음
- 보상형은 사용자가 광고와 보상을 알고 직접 동의

### 5.2 피해야 할 흐름

- 검색 결과에서 들어오자마자 전체 화면 광고
- 첫 퍼즐 시작 전 강제 광고
- 마지막 숫자를 입력한 즉시 예고 없이 광고
- 퍼즐 플레이 중 탭 복귀·첫 클릭을 광고로 가로채기
- 난이도 버튼과 일반 광고 단위를 한 모달에 배치
- 매 입력·매 힌트·매 셀 선택 후 광고
- 광고가 끝나지 않으면 정상 게임을 이용할 수 없게 함
- 광고 코드 또는 닫기 동작을 임의로 변경
- 운영자·테스터가 실제 광고를 클릭
- 광고 단위를 타이머로 직접 새로고침
- “사이트를 도와주세요” 같은 문구로 광고 클릭 유도

일반 AdSense 정책은 게시자가 사용자 요청 없이 페이지나 광고 요소를 자동 새로고침하는
것을 금지한다. 새 퍼즐 API 호출에 맞춰 일반 광고 단위를 수동 재요청하는 방식은
사용하지 않는다. H5 Ad Placement API가 제공하는 광고 기회·빈도 제어를 사용한다.

### 5.3 검색 노출 영향

Google Search는 방문 직후 본문을 가리는 침입형 interstitial이 검색 성과를 해칠 수
있다고 설명한다. 또한 전체적인 페이지 경험에서 과도한 광고와 침입형 interstitial을
피하도록 권장한다.

완주 후 사용자가 다음 게임을 요청할 때 표시하는 H5 광고는 방문 직후 콘텐츠를 막는
경우보다 위험이 낮다고 추론할 수 있다. 하지만 검색 순위에 영향이 없다고 보장할 수는
없다. 다음 규칙을 유지한다.

- 첫 랜딩·첫 게임에는 광고 없음
- 검색엔진과 사용자에게 다른 광고 경험을 제공하지 않음
- 법적 동의 모달 외에 초기 전체 화면 요소 없음
- 광고로 Core Web Vitals와 모바일 조작성 악화 여부 측정

## 6. 개인정보·동의·고지

### 6.1 Google 요구

AdSense 태그가 있는 페이지는 광고가 실제 표시되지 않아도 click tracker나 impression
pixel을 요청할 수 있다. Google은 모든 게시자가 쿠키 사용을 알리는 개인정보처리방침을
명확하게 공개하도록 요구한다.

처리방침에는 실제 설정에 따라 다음이 포함돼야 한다.

- Google을 포함한 제3자 광고 사업자
- 광고 쿠키 사용 목적
- 이전 방문을 기반으로 광고가 제공될 수 있다는 사실
- 개인 맞춤 광고 거부 방법
- 추가 광고 기술 제공자와 거부 경로
- 사이트가 자체 수집하는 이벤트·보존기간·문의 방법

EEA·영국·스위스 사용자에게 개인 맞춤 광고를 제공하려면 Google 인증 CMP와 IAB TCF
연동이 요구된다. 미국의 적용 주에서는 판매·공유·맞춤 광고 거부 메시지가 필요할 수
있다. AdSense의 `Privacy & messaging`은 유럽·미국 메시지를 지원하지만, 도구를
사용했다는 사실만으로 각 법률 준수가 보장되는 것은 아니다.

### 6.2 한국

개인정보보호위원회의 2026년 개인정보 처리방침 작성지침이 현재 안내서다. 공식
자료는 행태정보 수집·이용·제공과 거부 방법을 처리방침에 투명하게 공개하도록
안내한다. 특히 제3자가 웹사이트에서 수집도구로 행태정보를 수집하도록 허용한 매체
사업자는 그 내용을 웹사이트별 처리방침에 포함하는 방향을 제시한다.

광고를 도입하면 현재의 “개인정보를 거의 수집하지 않는 게임” 상태가 바뀐다. 최소한
`개인정보처리방침` 링크는 사용자가 볼 수 있어야 하므로 UI 완전 무변경은 불가능하다.
게임판을 훼손하지 않는 작은 footer 링크로 분리할 수는 있다.

### 6.3 동의 전 로딩

광고 SDK의 로딩 시점은 지역·동의 설정과 함께 설계해야 한다.

1. 필요한 지역에서 CMP 메시지를 표시한다.
2. 사용자의 선택을 확보한다.
3. 허용되는 광고 모드에 맞춰 태그를 초기화한다.
4. 동의가 없거나 도구가 실패해도 게임은 정상 작동한다.

광고와 퍼즐 생성의 실패 경로를 결합하면 안 된다. 광고 차단이나 CMP 실패가
`/api/new-puzzle/` 요청을 막아서는 안 된다.

## 7. 권장 기술 구조

### 7.1 모듈 경계

실제 구현 시 광고를 게임 로직에 직접 흩뿌리지 않고 한 어댑터로 격리한다. 신규 파일을
만든다면 저장소 규칙에 따라 `codex-mhj_26_08_27_04_` 접두어를 사용한다.

책임:

- CMP와 광고 API 준비 상태
- 테스트·프로덕션 모드 분리
- 마지막 광고 시간과 완료 횟수
- Classic·Rush placement 이름
- `adBreak()` 호출
- `placementInfo.breakStatus` 계측
- 광고 차단·초기화 실패 시 즉시 통과
- 중복 완료 방지

게임 측은 “다음 게임을 시작할 의도”만 전달하고, 광고가 나왔는지 여부를 판단하지
않는다.

### 7.2 상태 전이

```text
PLAYING
  -> COMPLETED
  -> RESULT_VISIBLE
  -> USER_REQUESTS_NEXT
  -> ELIGIBILITY_CHECK
       -> NOT_ELIGIBLE -> NEXT_GAME
       -> ELIGIBLE -> AD_OPPORTUNITY
            -> VIEWED / DISMISSED / NO_AD / CAPPED / ERROR / TIMEOUT
            -> NEXT_GAME
```

모든 광고 결과는 `NEXT_GAME`으로 합류해야 한다. 광고는 게임을 영구적으로 막을 수
없다.

### 7.3 Classic 연결

1. 완주 시 세션의 광고 적격 완료 횟수를 증가시킨다.
2. `새 게임` 난이도 모달은 기존 방식으로 연다.
3. 사용자가 난이도를 선택하면 모달을 닫는다.
4. 퍼즐 API 요청과 광고 기회를 동시에 시작한다.
5. 광고 종료와 퍼즐 검증이 모두 완료되면 새 보드를 반영한다.
6. 광고 API가 준비되지 않으면 퍼즐만 기다린다.

생성 알고리즘과 단서 수 랜덤 선택은 바꾸지 않는다. 광고 때문에 퍼즐 생성 CPU 시간이
늘지 않는다. 다만 광고가 실제 표시된 경우 사용자가 느끼는 전환 시간은 광고 길이만큼
늘어난다.

현재 `restart()`는 요청과 화면 반영이 하나로 묶여 있다. 병렬 처리를 하려면 내부를
“퍼즐 요청·검증”과 “세션 교체”로 나누되 공개 인터페이스와 API 계약은 유지해야 한다.

### 7.4 Rush 연결

1. `gameOver()`는 현재처럼 입력·타이머를 중지한다.
2. 결과 패널을 표시한다.
3. `다시 하기` 클릭에서 광고 적격성을 평가한다.
4. 적격이면 `type: next` 광고 기회를 선언한다.
5. `adBreakDone` 이후 `game.start()`를 호출한다.
6. 광고가 없거나 오류이면 바로 `game.start()`를 호출한다.

Rush의 `source.prime()`과 내부 prefetch를 유지한다. 광고 중 새 퍼즐을 준비하더라도
화면 뒤에서 플레이 상태를 시작하면 안 된다.

### 7.5 초기화와 timeout

`adConfig({ onReady })`는 광고 API 초기화와 preload 완료를 알려준다. 공식 문서도
`onReady`가 지연되거나 전혀 호출되지 않을 수 있으므로 timeout을 두고 게임을 계속할
것을 권장한다.

권장 동작:

- 광고 준비 상태는 게임 시작을 막지 않음
- 초기화 제한시간 2초
- 준비 전 광고 기회는 생략
- `adBreakDone`은 한 번만 처리
- 광고 중 페이지 숨김·복귀에도 게임 입력 잠금 유지
- 광고 종료 후 이전 포커스를 결과 또는 새 보드의 안정된 위치로 이동

### 7.6 테스트 모드

H5 태그의 `data-adbreak-test="on"`은 실제 광고 요청 없이 모의 광고를 표시한다.
테스트 모드는 광고가 있는 경우와 없는 경우를 번갈아 재현하며 설정된 빈도도 흉내 낸다.

필수 테스트:

- 광고 표시 후 정상 재시작
- `noAdPreloaded`
- `notReady`
- `frequencyCapped`
- `error`
- 광고 차단 확장 프로그램
- 오프라인
- 느린 광고 초기화
- 빠른 연속 클릭
- Escape·브라우저 뒤로 가기
- 모바일 회전·크기 변경
- 키보드·스크린리더 포커스 복원
- 광고 중 퍼즐 API 성공·실패

개발·QA 중에는 실제 광고를 클릭하지 않는다.

### 7.7 CSP와 외부 스크립트

현재 사이트에는 CSP가 없다. 광고 태그를 추가하면 외부 스크립트와 광고 iframe이
새로운 공급망이 된다. CSP를 동시에 강제 적용하면 Google 광고 도메인이 변할 때 광고나
게임이 깨질 수 있다.

권장 순서:

1. 광고 기능과 별도로 `Content-Security-Policy-Report-Only` 관찰
2. 실제 위반 보고를 기반으로 정책 구성
3. 게임 자체 script를 우선 nonce/hash 기반으로 제한
4. 광고 플랫폼 공식 CSP 지침과 SafeFrame 지원 확인
5. 충분한 관찰 후 강제 정책 전환

Google Publisher Tag 문서는 광고 도메인이 변할 수 있어 단순 도메인 allowlist보다
nonce를 사용하는 strict CSP를 지원한다고 설명한다. H5 AdSense 태그에 동일 구성을
그대로 적용할 수 있다고 가정하지 말고 실제 테스트해야 한다.

| 상황 | Classic | Rush |
|---|---|---|
| 첫 방문·첫 게임 | 광고 없음 | 광고 없음 |
| 미완성 포기 | 광고 없음 | 해당 없음 |
| 완료 후 다음 게임 | 완료 2판마다 기회 | 종료 3판마다 기회 |
| 최소 시간 간격 | 10분 | 10분 |
| 탭 복귀 | 광고 없음 | 광고 없음 |
| 광고 실패·차단 | 즉시 진행 | 즉시 진행 |
| 보상형 | 초기 제외 | 초기 제외 |

완료 횟수와 10분 조건을 모두 충족할 때만 `adBreak()` 기회를 선언한다. 실제 광고는
API의 재고와 frequency cap에 따라 더 적게 표시될 수 있다.

### 8.2 왜 매 판이 아닌가

스도쿠 한 판은 사용자가 상당한 집중 시간을 투자하는 활동이다. 매 판 광고는 광고
기회 수는 늘리지만 다음 판 전환과 재방문을 떨어뜨릴 수 있다. 광고가 수익을 늘려도
완주량이 줄면 장기 총 노출은 감소할 수 있다.

최적화 대상은 광고 `eCPM`이 아니라 다음이다.

- 방문자당 순수익
- 완료 1,000회당 순수익
- 광고 전후 다음 판 시작률
- 광고 전후 재방문율

## 9. 수익 민감도

### 9.1 공식적으로 알 수 없는 값

Google은 이 사이트의 H5 Games Ads `eCPM`, fill rate, show rate를 보장하거나 공개하지
않는다. 광고 형식·언어·국가·기기·동의·광고 수요·계절에 따라 달라진다. 따라서 아래
수치는 매출 예측이 아니라 손익 구조를 이해하기 위한 산술 시나리오다.

### 9.2 계산식

```text
광고 기회 = 완료 횟수 × 광고 기회 비율
실제 노출 = 광고 기회 × 노출률
매출 = 실제 노출 ÷ 1,000 × eCPM
```

기본 시나리오 가정:

- 완료 2회당 광고 기회 1회: `50%`
- 기회 중 실제 광고 노출률: `60%`
- 완료 1회당 실제 광고 노출: `0.3회`

### 9.3 월 완주량별 계산

| 월 완주 | 실제 광고 노출 가정 | eCPM $0.5 | eCPM $2 | eCPM $5 | eCPM $10 |
|---:|---:|---:|---:|---:|---:|
| 10,000 | 3,000 | $1.50 | $6 | $15 | $30 |
| 50,000 | 15,000 | $7.50 | $30 | $75 | $150 |
| 100,000 | 30,000 | $15 | $60 | $150 | $300 |
| 500,000 | 150,000 | $75 | $300 | $750 | $1,500 |

광고가 한 번 표시될 때 사용자가 여러 광고 impression을 만들 가능성이나 광고 형식별
계수는 이 단순 모델에 포함하지 않았다. 실제 AdSense 보고서 값을 확보하면 모델을
폐기하고 관측값으로 교체한다.

### 9.4 USD $100 지급 기준 시나리오

계정의 보고 통화가 USD인 경우 공식 지급 기준은 $100이다. 같은 기본 가정에서 한 번의
$100 누적에 필요한 완료 횟수는 다음과 같다.

| 가정 eCPM | 필요한 광고 노출 | 필요한 완주 |
|---:|---:|---:|
| $0.5 | 200,000 | 약 666,667 |
| $2 | 50,000 | 약 166,667 |
| $5 | 20,000 | 약 66,667 |
| $10 | 10,000 | 약 33,334 |

이는 월 기준이 아니다. 해당 완주량을 달성하는 데 여러 달이 걸리면 지급도 그만큼
늦어진다. 실제 지급 통화와 기준은 계정 설정에서 확인해야 한다.

### 9.5 수익 배분 해석

AdSense for Content의 공식 설명은 광고 구매 플랫폼 수수료 차감 후 게시자에게 80%를
지급하며, Google Ads가 구매 플랫폼인 예시는 광고주 지출의 약 68%가 게시자에게
돌아간다고 설명한다. Google은 모든 AdSense 상품의 배분율을 공개하지 않으며 H5
상품의 실제 계정 수치는 계정에서 확인해야 한다.

따라서 68%를 H5 게임 광고의 별도 추가 계산 계수로 다시 차감하면 안 된다. AdSense
보고서의 게시자 수익과 `eCPM`은 지급 관점의 관측값으로 사용한다.

## 10. 측정 설계

### 10.1 광고 도입 전 28일 기준선

- 방문자·방문·국가·기기
- Classic 새 퍼즐 요청 수
- Classic 완주 수
- Classic 완주 후 새 게임 선택률
- Rush 시작·종료·다시 하기 수
- 세션당 판 수
- 1일·7일 재방문
- 퍼즐 API 오류율과 응답시간
- Core Web Vitals

현재 Cloudflare Web Analytics만으로 완주와 재시작을 알 수 없다. 개인 식별자를 만들지
않는 집계 이벤트 설계가 추가로 필요하다. 어떤 이벤트를 어디에 보존하는지 개인정보
처리방침과 일치해야 한다.

### 10.2 광고 이벤트

- `ad_opportunity`
- placement 이름과 모드
- `breakStatus`
- 광고 전후 다음 게임 시작 성공
- 광고 초기화 timeout
- 광고 차단 또는 SDK 미사용 경로

H5 Ads 성과는 AdSense의 `Ad format` 보고서에서 `Interstitial`과 `Rewarded`로 나눠
확인한다. Rewarded의 click은 물리 클릭과 engaged view가 함께 잡힐 수 있으므로 CTR과
CPC 해석에 주의해야 한다.

### 10.3 핵심 지표

| 지표 | 목적 |
|---|---|
| 완료 1,000회당 광고 수익 | 제품 활동과 수익 직접 연결 |
| 광고 기회 대비 실제 노출률 | 재고·동의·빈도 영향 |
| 광고 후 다음 게임 시작률 | 즉시 이탈 영향 |
| 광고·무광고 세션당 판 수 | 참여도 영향 |
| 광고·무광고 D1/D7 재방문 | 장기 영향 |
| 광고 초기화 실패율 | 안정성 |
| Core Web Vitals 변화 | 성능·검색 위험 |
| 국가·언어별 eCPM | 수익 구성 |

페이지 RPM만 보면 현재 단일 페이지 게임의 실제 플레이 활동을 설명하지 못한다.
완주와 광고 노출을 연결한 지표가 필요하다.

## 11. 실험 설계와 중단 기준

### 11.1 선행 게이트

아래 조건을 모두 충족하기 전에는 실제 광고를 배포하지 않는다.

- [ ] 독립 도메인 또는 AdSense가 승인한 사이트 주소
- [ ] AdSense 사이트 `Ready`
- [ ] H5 Games Ads 승인
- [ ] 개인정보처리방침 공개
- [ ] 지역별 CMP·거부 경로 검토
- [ ] `ads.txt` HTTP `200`과 Authorized 상태
- [ ] 무광고 28일 기준선
- [ ] 테스트 모드 전체 경로 통과
- [ ] 광고 차단 상태에서 게임 정상 동작
- [ ] 모바일·키보드·스크린리더 검증

### 11.2 Rush 우선 롤아웃

1. 내부·테스트 모드 100%
2. 실제 사용자 10%
3. 최소 1주 관찰
4. 오류와 이탈 문제가 없으면 25%
5. 50% 대조 실험
6. 실제 수익과 유지율이 모두 통과하면 100%

트래픽이 적으면 1주 데이터로 결론을 내릴 수 없다. 표본 수와 요일 편차를 확인하고
충분한 완료·광고 노출이 쌓일 때까지 연장한다. 한 실험에서는 빈도·배치·형식 중 하나만
바꾼다.

### 11.3 초기 중단 기준

아래 항목은 프로젝트 내부 운영 기준이며 광고 플랫폼 공식 기준이 아니다.

- 광고 또는 CMP 때문에 새 게임이 시작되지 않는 오류 1건이라도 재현되면 즉시 중지
- 광고 경로 기술 오류율이 `0.5%`를 넘으면 확대 중지
- 광고 후 다음 게임 시작률이 대조군보다 `5%p` 이상 하락하고 반복 관찰되면 중지
- D1 또는 D7 재방문이 유의미하게 악화되면 빈도 축소 또는 중지
- Core Web Vitals가 `good` 범위를 벗어나면 성능 수정 전 확대 중지
- 정책 경고·무효 트래픽 경고가 발생하면 해당 배치 즉시 중지
- 실제 완료 1,000회당 수익이 운영자가 정한 최소값보다 낮으면 중지

광고 수익이 늘어도 완주와 재방문이 줄면 실패로 판단한다.

## 12. 도입 단계

### 단계 A — 광고 없이 준비

- 독립 도메인 연결
- 실제 운영자·문의 정보 결정
- 개인정보처리방침 작성
- 무광고 이벤트 기준선 구축
- 사이트 기능 페이지 보강
- Search Console·Naver·Bing과 방문 분석 연결

### 단계 B — 승인

- AdSense 사이트 등록·소유 확인
- CMP 옵션 선택
- 사이트 검토 요청
- 승인 후 H5 Games Ads 신청
- 거절 사유와 재신청 가능성 기록

승인 전 광고용 보상 경제나 복잡한 SDK 래퍼를 개발하지 않는다.

### 단계 C — 테스트 구현

- 광고 어댑터 추가
- 테스트 태그만 연결
- Rush `다시 하기`에 `next` placement 연결
- Classic 완료 상태 계측
- timeout·무재고·차단 fail-open 구현
- 자동·수동 접근성 회귀 테스트

### 단계 D — Rush 실제 실험

- 10분 간격
- 종료 3회당 기회 1회
- 첫 게임 광고 없음
- 10%부터 단계 확대
- 수익과 다음 게임 전환 동시 평가

### 단계 E — Classic 또는 보상형

Rush 실험이 통과한 경우에만 진행한다.

- Classic: 완료 2회당 다음 게임 광고 기회
- 퍼즐 생성과 광고 병렬화
- 보상형: 제품적으로 필요한 보상이 확인될 때만

### 단계 F — 대체 경로

AdSense 또는 H5 승인이 되지 않으면 다음 순서로 검토한다.

1. Rush의 CrazyGames Basic Launch
2. 관련 기관·출판사 직접 스폰서 결과 카드
3. 별도 콘텐츠 페이지의 일반 디스플레이 광고
4. Poki는 웹 독점·수익배분 계약을 검토한 뒤 결정

여러 광고 SDK를 한 빌드에 동시에 넣지 않는다. 포털별 빌드는 각각의 SDK·광고 정책에
맞춰 분리해야 한다.

- 승인 가능성을 모른 채 광고 코드부터 대규모 구현
- 자체 모달 안에 일반 AdSense 단위 삽입
- 첫 방문 Vignette 활성화
- Auto Ads 추가 트리거를 게임 페이지에서 기본 허용
- 새 퍼즐마다 일반 광고 수동 갱신
- 실제 RPM 없이 매출 확정
- 유료·교환 트래픽으로 광고 impression 구매
- 자체 광고 클릭 또는 지인에게 클릭 요청
- 개인정보처리방침 없이 광고 태그 배포
- H5와 포털 SDK를 같은 배포본에서 동시에 운영
- 광고 때문에 기존 퍼즐 생성·유일해 검증 로직 변경

## 14. 최종 판단

### 현실성 순위

1. **Rush 완료 후 H5 Interstitial** — 승인된다면 가장 자연스러운 자사 광고 모델
2. **직접 스폰서 결과 카드** — 소수 B2B 관계가 생길 경우 낮은 트래픽에서도 가능
3. **CrazyGames의 Rush 배포** — 자체 검색과 무관한 외부 트래픽 검증 수단
4. **Classic 완료 후 H5 Interstitial** — 플레이 시간이 길어 노출 규모가 제한됨
5. **H5 Rewarded** — 유효한 보상 설계가 생긴 뒤
6. **일반 디스플레이·Vignette** — 현재 집중형 UI에는 부적합

### 경제성 판단

기본 시나리오에서는 월 100,000회 완주가 있어도 `eCPM $2`라면 계산상 월 $60이다.
현재 완주량이 확인되지 않은 상태에서 광고 구현을 우선하는 것은 합리적이지 않다.
먼저 기준 데이터를 수집하고, 승인 가능성을 확인한 뒤, Rush의 자연 전환 한 곳만
실험하는 것이 최소 위험 경로다.
